# Kaggle枝を脇に置き、EPS製品価値へ戻る

## 結論

Kaggle/Bosch方向は、需要調査としては有用だった。
ただし、本Repoの本題である「EPS製品そのものにどんな付加価値を載せられるか」からは外れる。

理由は単純である。
Bosch型の出荷前品質スクリーニングは、製造品質、EOL検査、工程改善の話である。
これはビジネスモデル候補にはなり得るが、EPSの市場投入後の製品価値、OEM向け機能価値、車両側の差別化価値ではない。

したがって、Kaggle枝は以下の位置づけに下げる。

> EPSサプライヤ工場向けの製造品質・検査工程分析として、需要調査だけ継続してよい。ただし、Repoの主仮説にはしない。

本題に戻る。

## 何が分かったか

Kaggle/Boschから分かったこと:

- 自動車系企業は、製造不良予測やテスト時間短縮を外部課題として出すことがある
- 出荷前の品質予兆検知には、一定の業務需要がありそうである
- EPSサプライヤが持てる工程、EOL、検査、評価データに寄せられる
- ただし、これは製造品質や工程改善の文脈であり、EPS製品価値ではない

この枝で言ってよいこと:

> EPSサプライヤ内部の製造品質・EOL検査・工程改善向けには、出荷前品質スクリーニングの需要がありそうである。

この枝で言ってはいけないこと:

> EPS製品の付加価値が見つかった。

> EPSの出荷後故障予測ができる。

> OEM向けの製品差別化になる。

## なぜ本題ではないか

本Repoが本来探していたのは、以下である。

> EPSサプライヤが、EPSという製品にどんな付加価値を載せられるか。

Kaggle/Bosch線の買い手は、製造品質、EOL検査、工程設計、工場品質保証である。
これはサプライヤ内部の工場業務であり、EPS製品を買うOEMや、EPS製品仕様に載る価値とは別である。

したがって、この線を深掘りしすぎると、Repoは「EPS製品価値探索」ではなく「製造品質分析サービス探索」になる。
それは別テーマとしてはありだが、現在の本題ではない。

## 本題へ戻すための判断

今後の探索は、次の条件を満たすものだけを本題として扱う。

1. EPS製品仕様、診断仕様、制御仕様、評価仕様、説明責任のどれかに載る
2. EPSサプライヤが部品境界で実施または説明できる
3. OEM保証DB、fleet data、サービス領域を初期前提にしない
4. 既存DTC、freeze frame、extended data、安全設計、診断設計の言い換えではない
5. 買い手または利用者が、製造工場だけに閉じない

この条件を満たさないものは、枝として残しても主仮説にしない。

## 次に戻るべき探索軸

現時点で、本題に戻るなら候補はかなり限られる。

### 1. EPS製品仕様に載る「説明可能な運用限界」

市場需要:

SbW、ADAS、ドライバ支援、高機能EPSでは、どの条件でassistが制限され、どの状態で警告し、どこまで操舵能力が残るかを分かりやすく説明する必要が増える。

未解決の痛み:

安全設計や診断設計には既存成果物があるが、OEM説明、RFQ回答、診断コンテンツ、ユーザ警告の間で、言ってよいことと言ってはいけないことがずれやすい。

仮説:

EPSサプライヤは、assist制限、degraded state、warning、DTC、software/calibration条件を、製品仕様に近い自然言語で整理することで価値を出せるかもしれない。

注意:

これは過去のSbW説明支援に近く、既存安全・認証業務と被る。
再開するなら、「既存資料の要約」ではなく、製品仕様・診断仕様に残る形かどうかだけを見る。

### 2. EPS診断コンテンツの次世代化

市場需要:

車両診断はSOVDなど次世代化が進む。
OEM診断基盤はOEM領域だが、EPSサプライヤはDTC、DID、freeze frame、extended data、software ID、security accessなどの診断コンテンツを持つ。

未解決の痛み:

次世代診断基盤へ載せるとき、EPS側の診断コンテンツをどう見せ、何を隠し、どの権限で読ませるかは製品側の判断が必要になる。

仮説:

EPSサプライヤは、診断コンテンツの構造化、公開/制限、説明文、権限、software/calibrationとの紐付けを整理することで、OEM向けの製品付加価値を出せるかもしれない。

注意:

SOVD基盤やODX/UDS変換ツールは追わない。
追うのはEPS診断コンテンツそのものだけである。

### 3. EPS製品の「禁止主張リスト」付きRFQ/仕様回答支援

市場需要:

OEM RFQや技術問い合わせでは、EPSがどこまで説明できるか、どこからOEM車両側データが必要かを明確にしたい。

未解決の痛み:

故障予測、劣化兆候、保証費削減、root cause断定など、言い過ぎると責任範囲を超える主張が混ざりやすい。

仮説:

EPSサプライヤは、製品仕様・診断仕様・評価仕様から、言えること/言えないことを明確にしたRFQ回答材料を作れるかもしれない。

注意:

過去のRFQ / Design Review Pack単体はKill済み。
再開するなら、一般論ではなく、EPS製品仕様に残る文言と禁止主張の整理に限定する。

## 現時点の優先順位

本題へ戻すなら、優先順位は以下。

| 優先 | 探索軸 | 理由 | リスク |
|---:|---|---|---|
| 1 | EPS診断コンテンツの次世代化 | EPSサプライヤが持つDTC/DID/freeze frame/software IDに近い | OEM診断基盤や既存ツール領域に飲まれやすい |
| 2 | 説明可能な運用限界 | SbW/ADAS時代の製品説明に近い | 既存安全・認証資料の要約になりやすい |
| 3 | 禁止主張付きRFQ/仕様回答 | EPSサプライヤの責任境界を守る価値がある | 一般論や資料整理に落ちやすい |
| 枝 | 出荷前品質スクリーニング | 需要はありそうだが工場業務であり本題ではない | 製造品質分析サービスへ逸れる |

## 次アクション

本題に戻るなら、次は次世代診断コンテンツを見直すのがよい。

見るべき問い:

1. EPSサプライヤが持つ診断コンテンツは何か
2. それは次世代診断でどう見せる必要があるか
3. OEM診断基盤ではなく、EPS製品側で整理できる範囲はどこか
4. 既存DTC/freeze frame/extended dataの言い換えで終わらない差分はあるか
5. どの成果物ならEPS製品仕様、診断仕様、RFQ回答に残るか

Kill条件:

- SOVD基盤、ODX変換、UDS toolingの話になる
- OEM診断プラットフォームに依存する
- 既存DTC表の整形で終わる
- 買い手が「診断設計担当が既にやっている」で止まる
- EPS製品仕様に残る価値がない

## 最終判断

Kaggle/Bosch線はKillではない。
ただし、本題ではない。

Repoの主探索は、EPS製品価値へ戻す。
次に掘るなら、製造工程ではなく、EPS診断コンテンツの次世代化と製品仕様に残る説明価値を見る。
