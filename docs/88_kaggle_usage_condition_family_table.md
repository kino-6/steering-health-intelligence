# Kaggle使用条件family表

## 最新ルールでの位置づけ

この表は、現行探索の主成果物ではない。
現行探索の主目的は、Kaggle / 公開proxyから、EPSサプライヤが「予測のような付加価値」を作れる余地があるかを見ることである。

したがって、「実使用条件からEPS評価・診断の問いを作る」ことは主目的ではない。
評価scenario、診断質問、顧客説明質問は、予測的な付加価値候補を検証するための副次artifactとして扱う。
この表を読むときは、各usage familyについて「何を先読みできる可能性があるか」「それがEPSサプライヤの価値になるか」「何を予測したと言ってはいけないか」を次に確認する。

## 結論

Kaggleを、EPS故障予測を実証する材料やモデル精度競争として使わない。
ただし現行探索では、公開Kaggleデータから読み取れる運転行動、操舵要求、路面・振動、通信異常が、EPSサプライヤにとって予測のような付加価値へ変わるかを見る。

この文書は、そのための中間成果物である。
公開proxyをまず使用条件familyへ分け、次に「何を先読みできる可能性があるか」「誰の業務価値になるか」「何を予測したと言ってはいけないか」へ変換するための作業面として使う。
評価scenario、診断質問、顧客説明質問は、その検証を進めるための副次artifactである。

作成した成果物は [data/kaggle_usage_condition_families.tsv](../data/kaggle_usage_condition_families.tsv) である。
全30件の使用条件familyを、公開proxy、先読み候補、評価scenario、診断質問、顧客説明質問、禁止主張へ対応付ける土台として使う。

## 何を判断しているか

判断しているのは、EPSが壊れるかどうかではない。
判断しているのは、公開proxyだけで、EPSサプライヤが次のような「先読み候補」を作れるかである。

- 低速高操舵が多い使われ方を先読みまたは分類できるか。
- 荒れた路面と操舵入力が重なる負荷条件を先読みまたは分類できるか。
- stop-startや急加減速が多い使われ方を、EPSの使用負荷classとして読めるか。
- 通信異常やspoofingのcontextを、EPS故障と誤認しないための異常contextとして読めるか。

## 作った分類

| 分類 | 主なsource ID | 使い道 |
|---|---|---|
| 操舵要求 | KGL005, KGL003 | 操舵角、操舵変化、低速高操舵、急操舵を評価scenarioへ落とす |
| 運転行動 | KGL003, KGL007, KGL010 | stop-start、急加減速、aggressive driving、traffic状態を使用条件familyへ落とす |
| 路面・振動 | KGL006, KGL007, KGL008 | 荒れた路面、段差、連続振動、都市部低速走行を外乱条件へ落とす |

| 補助context | KGL009, KGL010, KGL012 | schemaや熱・EV実走行contextの補助列として使う |

## 使い方

この表は、外販商品ではなく、次のレビューに持ち込むための作業面である。

評価企画に見せる場合:

- 既存HILS/bench/vehicle評価で、各usage familyを見ているかを確認する。
- 既存評価があるなら、どの試験名、どの入力条件、どの判定基準かを確認する。
- 既存評価がないなら、公開proxyから見て追加質問に値するかを確認する。

診断コンテンツ担当に見せる場合:

- DTCやfreeze frameだけで、使われ方や外部条件を説明できるかを見る。
- 説明できない場合でも、追加ログや新商品に飛ばず、まず「何を言ってはいけないか」を整理する。

顧客技術説明に見せる場合:

- 顧客に説明できるのは、使用条件や外部条件の可能性までである。
- 故障原因、残寿命、保証費削減、内部状態は断定しない。

## 優先度

次に深掘りするなら、優先度は以下である。

1. `UF001〜UF010`: 操舵要求と運転行動の基本family
2. `UF011〜UF020`: 路面・振動と複合条件
3. `UF021〜UF025`: 交通状態、熱、EV実走行context
4. `UF026〜UF030`: 通信異常と禁止主張

最初のレビューでは、全30件を使わず、まず `UF001`, `UF002`, `UF005`, `UF011`, `UF013`, `UF017`, `UF026`, `UF028` の8件だけ見ればよい。
この8件で、評価・診断・顧客説明へ転記できないなら、残りを増やしても価値は出にくい。

## EPSサプライヤとしての言い方

言ってよいこと:

> 公開KaggleデータはEPS内部状態を示さないが、実使用条件、操舵要求、路面・振動、通信異常を読むproxyとして使える。これらを評価scenario、診断質問、顧客説明質問、禁止主張へ変換できるかを見る価値がある。

まだ言ってはいけないこと:

> KaggleでEPS故障予測を実証できる。

> 公開proxyでEPS内部状態、DTC不足、thermal limit、assist limitationを断定できる。

> 通信異常datasetでEPS/SbW cyber商品を作れる。

> 路面分類や操舵角推定をそのままEPSサプライヤ商品として売れる。

## Kill条件

この表は、次のどれかに当たれば止める。

- usage familyが既存評価scenario、診断質問、顧客説明質問へ転記できない。
- 公開datasetの紹介で終わる。
- EPS内部状態や故障原因を断定し始める。
- ADAS制御、road quality product、generic IDS/cyber productへ流れる。
- OEM保証DB、fleet data、service outcomeがないと価値が出ない方向へ戻る。
