# OEM Usage Translation Minimum Pack

## 結論

次に作るべきものは、外部データをさらに掘る調査ではない。
OEMが想定する車両用途や使われ方を受け取ったときに、EPSサプライヤ側で何を確認し、何を提案し、何を言ってはいけないかへ翻訳する4枚の社内レビュー資料である。

この4枚は、売り物の完成版ではない。
製品企画、診断企画、品質改善、評価企画、顧客技術説明、サイバー担当が、既存成果物に貼れる具体用途を挙げられるかを見るための最小パックである。

対応表は [data/oem_usage_translation_minimum_pack.tsv](../data/oem_usage_translation_minimum_pack.tsv) に置く。

## 何を判断しているか

判断しているのは、公開proxyからEPS故障、残寿命、交換時期を予測できるかではない。
駐車場や荒れた路面を、有望用途としてEPSサプライヤが勝手に定義できるかでもない。

判断しているのは、次である。

> OEMの用途想定を受けたとき、EPSサプライヤが自社の製品企画、診断企画、品質改善、評価企画、顧客技術説明へ転記できる確認観点を作れるか。

公開proxyは、OEM用途を決めるためではなく、EPSサプライヤ側が事前に返すべき質問を準備するために使う。

## Rule Check

今回の判断では、[AGENTS.md](../AGENTS.md) の次を適用する。

1. `Market Demand First`
2. `Natural Language First`
3. `EPS Supplier Lens`
4. `Kaggle / Public Proxy Predictive Value Rule`
5. `OEM Usage Translation Rule`
6. `Mandatory Rule Check Before Stop / Kill / Archive`

この文書では、StopやArchiveを主結論にしていない。
ただし、各sheetにKill条件を置くため、次を確認する。

- Kill理由を、EPS内部状態、DTC、freeze frame、交換結果が見えないことだけにしない
- OEM用途コンセプトをEPSサプライヤが代替定義する話にしない
- 公開proxyを、EPS内部stress、故障原因、残寿命の代替にしない
- 判断軸を、EPSサプライヤの業務成果物へ転記できるかに置く
- 汎用テレマティクス、路面分類、ADAS、IDSと区別できるかを見る

## 4枚の最小パック

### 1. 製品企画向け: OEM用途想定をEPS価値説明へ翻訳する

判断すること:

> OEMが低速、反復操舵、大舵角、段差、路面外乱を含む用途を想定しているとき、それをEPSの価値説明やRFQ確認質問へ変換できるか。

このsheetは、駐車場を新しく発見する資料ではない。
駐車場や狭い市街地、配送拠点、構内移動のような使われ方は、OEM側の用途想定として出てくる前提で扱う。
EPSサプライヤ側の仕事は、それを低速取り回し、操舵感、路面外乱下の体感、電源や温度の確認質問へ分解することである。

初期出力:

- OEM用途想定の読み替え表
- RFQで確認する質問
- 製品価値として言ってよい表現
- 故障予測や耐久優位に見えるため避ける表現

Proceed条件:

- 製品企画が、既存カタログや既存RFQ回答にはない確認質問を挙げられる
- 低速取り回し、操舵感、路面外乱下の体感を、故障しにくさではなく製品価値として説明できる
- 次に確認したいOEM用途、車格、サービス、運行シーンを具体化できる

Kill条件:

- 既存カタログやRFQ回答と同じ言葉にしかならない
- 価値説明に、故障しにくさ、残寿命、保証費削減が必要になる
- OEM用途コンセプトの定義に入り込み、EPSサプライヤの手札から外れる

### 2. 診断企画向け: OEM用途想定を使用context説明の境界へ翻訳する

判断すること:

> OEM用途想定に低速反復操舵や路面外乱が含まれるとき、DTCやfreeze frameだけでは説明しにくい使用contextを、診断説明の境界として扱えるか。

このsheetは、DTCを増やす提案ではない。
故障予測でもない。
既存診断値を読むときに、どこまで使用contextとして説明してよいか、どこから先はEPS内部状態やDTCがないと説明してはいけないかを分ける資料である。

初期出力:

- 既存診断で見える項目
- 公開proxyや用途想定から推測ではなく質問として置ける項目
- 顧客説明で使ってよい言い方
- 原因断定、責任転嫁、保証判断に見えるため避ける言い方

Proceed条件:

- 診断企画が、既存DTC / freeze frame / extended dataだけでは使用context説明が粗いと言える
- 診断読み順、追加確認項目、顧客説明境界に転記できる
- DTC追加や故障予測ではなく、既存診断結果の読み方として扱える

Kill条件:

- 既存DTC / freeze frame / extended dataで同じ説明が十分できる
- 顧客説明に使うと原因断定や責任転嫁に見える
- 価値説明が、DTC追加、故障予測、保証判断へ流れる

### 3. 品質改善 / 評価企画向け: 荒れた路面と操舵を確認観点へ翻訳する

判断すること:

> OEM用途想定に荒れた路面、段差、連続振動、操舵入力が含まれるとき、品質改善や評価企画で見るべき確認観点へ変換できるか。

このsheetは、路面分類productではない。
また、荒れた路面がEPS故障原因だと言う資料でもない。
品質改善や評価企画が、既存NVH、耐久、路面評価と何が同じで、何が違う確認観点になるかを見る資料である。

初期出力:

- OEM用途想定から見た路面外乱と操舵の組み合わせ
- 品質改善でfield issueを読み直す入口
- 評価企画で既存評価の代表性を確認する質問
- 顧客技術説明で原因断定を避ける禁止主張

Proceed条件:

- 品質改善が、field issueを使用条件別に読み直す入口として使える
- 評価企画が、既存評価で足りる条件と追加確認すべき条件を分けられる
- 顧客技術説明が、路面外乱由来の体感とEPS異常を混同しない説明境界に使える

Kill条件:

- 既存NVH、耐久、路面評価scenarioの言い換えで終わる
- 路面分類や車両全体NVHの話になり、EPSサプライヤの手札から外れる
- 荒れた路面がEPS故障原因、内部劣化、thermal limitを示すように読まれる

### 4. 診断企画 / サイバー担当向け: 通信異常を診断信頼性境界へ翻訳する

判断すること:

> 通信異常があるとき、EPS診断値や操舵関連signalをどこまで信用してよいかを、診断企画とサイバー担当の間で分けられるか。

このsheetは、汎用IDS商品ではない。
CSMS、TARA、SOC運用の代替でもない。
通信異常がある場合に、EPS故障と誤認しないための診断信頼性境界と禁止主張を作る資料である。

初期出力:

- 通信異常type
- EPS診断説明で信用してよい情報
- 追加確認が必要な情報
- EPSサプライヤが言ってはいけないこと
- サイバー担当やOEM側へ渡すべき境界

Proceed条件:

- 診断企画が、通信異常時のDTC / freeze frame / signalの信用境界を必要としている
- サイバー担当が、既存CSMS/TARA/SOC/IDSとEPS診断説明の境界を分けられる
- 顧客技術説明が、通信異常とEPS故障を混同しない禁止主張として使える

Kill条件:

- 汎用IDS、CSMS、TARA、SOC運用の言い換えにしかならない
- EPS診断説明や診断読み順に転記できない
- SbW安全証明、EPS品質証拠、steering cyber productとして扱おうとする

## 社内レビューで聞く順番

最初に全員を集めない。
まず、製品企画と診断企画に見せる。
この2部署のどちらにも刺さらない場合、品質改善やサイバーへ広げても本線は弱い。

順番は以下である。

1. 製品企画: OEM用途想定をEPS価値説明とRFQ質問へ翻訳できるか
2. 診断企画: 同じ用途想定を使用context説明の境界へ翻訳できるか
3. 品質改善 / 評価企画: 荒れた路面と操舵を既存評価やfield issue整理と違う観点にできるか
4. 診断企画 / サイバー担当: 通信異常をEPS診断信頼性境界へ翻訳できるか

## EPSサプライヤとしての言い方

言ってよいこと:

> OEMの用途想定を受けたときに、低速反復操舵、路面外乱、通信異常のような観点を、EPSサプライヤ側のRFQ質問、評価確認、診断説明境界、顧客技術説明へ翻訳できるかを確認する。

まだ言ってはいけないこと:

> 公開proxyからEPS故障、残寿命、交換時期、安全性、保証費削減、root causeが分かる。

> 駐車場、荒れた路面、通信異常がEPS故障原因である。

> EPSサプライヤが公開proxyだけでOEMの車両コンセプトや厳しい用途を定義できる。
