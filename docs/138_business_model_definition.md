# Business Model Definition

## なぜこのドキュメントが必要か(自己批判)

docs/119〜137は、技術検証としては積み上がったが、「問題点に手当てできた」の集合であり、**事業の定義がなかった**。
誰が、何に対して、なぜ、どの形で金を払うのか。それが定義されていなければ、payload設計もcohort曲線も「メーカー作業者の改善活動」であって、このRepoの目的(事業仮説の検証)の成果物ではない。

本ドキュメントで、検証済みの材料をビジネスモデルとして定義し直す。

## 結論: ビジネスモデルは3層構造で、金が動くのは第1層である

| 層 | 名前 | 金の流れ | 位置づけ |
|---|---|---|---|
| **第1層(本体)** | **State-Explanation-Ready EPS**(状態説明機能を組み込んだEPS製品) | **OEMがEPS製品価格+診断コンテンツNREとして払う**。RFQでの採用・価格に反映 | 唯一の収益線 |
| 第2層(信用の裏付け) | 市場シグナル監視(cohort曲線運用) | 金は動かない。**サプライヤ品質業務への内部投資** | 第1層の営業トークを「実際にサプライヤでやっている」事実で裏付ける |
| 第3層(受け皿) | 固定スコープassessment(質問シート照合+payload仕様納品) | program付帯のNREとして小さく回収 | 単独外販はしない(既往Killと整合) |

一言で言うと:

> **EPSサプライヤは「サービス」や「予測」を売らない。「fault未満の機能低下を、原因断定なしの状態説明として自己申告できるEPS」という製品仕様を売る。** 買い手はOEMであり、支払いはRFQ採用と診断コンテンツNREの形で発生する。監視ツールや assessment はこの製品仕様を勝たせるための脇役である。

## Required Output Shape(AGENTS.md準拠)

| Field | 内容 |
|---|---|
| **Market demand** | OEMの品質・保証・サービス部門は、「症状はあるがコードがない」車両の誤診・空振り修理・NTFに実費を払い続けている(公式記録: gear誤交換の連鎖=17-NA-158、既払い修理の払い戻し=17276、DTC1bitで0.2h/3hが分岐=15S18)。さらにISO 21448運用フェーズ・in-service監視の義務化で、「市場投入後にfault未満の機能低下を説明し続ける能力」への要求が構造的に増えている |
| **Evidence signal** | docs/127(痛みの実在)、docs/129-130(是正実務の1bit判断)、docs/125(既存標準の設計選択の穴)、docs/126/128(SOTIF-EooC=規格上の部品参加形式、Boschの定量SOTIF武装)、docs/135-137(群レベルシグナルの実在と限界) |
| **Hypothesis** | OEMは、誤診コストと監視義務を減らす「部品側の状態説明能力」に対して、EPS選定時の差別化要素および診断コンテンツNREとして支払う。特にby-wire/SDV世代のRFQでは、この能力の有無が採点項目になる |
| **Solution** | ①EPS製品仕様としてのpayload機能(トリガ条件+数十バイトの不揮発記録+読み出しDID+言葉の境界ルール=docs/122)。②RFQ回答パッケージ(質問シート=docs/123、SOTIF-EooC接続=docs/126)。③サプライヤ運用の市場シグナル監視(docs/135-137)を営業上の実績として提示 |
| **Buyer / user** | **金を払う買い手: OEM**(購買+システム/診断設計。RFQの場)。使い手: OEMのサービス・品質・vehicle health基盤、およびEPSサプライヤ社内の品質改善・顧客技術説明 |
| **Why supplier can play** | 部品内部のfault未満観測は部品設計者にしか定義・実装できない(テレマ・OEM・プラットフォーマーには物理的に見えない=docs/125で確認済みの3つの穴)。Boschが手法(定量SOTIF)で武装するなか、非Bosch系サプライヤの対抗軸は「サプライヤ部品の内部観測の質」しかない |
| **EPS supplier conclusion** | 売る: 状態説明機能つきEPSという製品仕様+その診断コンテンツNRE。実施する: サプライヤ搭載車種の市場シグナル監視(内部投資)。売らない: fleet SaaS、予測サービス、SOTIF適合支援、監視ツール外販 |
| **Demo** | 4本のレポート(docs/132/135/136/137)+模擬runtimeデモ(次作業)。RFQの場で「絵に描いた餅ではない」を示す道具 |
| **What not to claim** | 個車RUL・交換時期・故障予測、root cause断定、保証費削減の約束、安全保証、SOTIF適合の証明、EPS無罪 |
| **Kill criteria** | 下記「ビジネスモデルのKill条件」 |

## 金の流れの具体形(第1層)

EPS事業の収益は「program採用×単価×数量+NRE」で決まる。本モデルはその**既存の金の流れの中で**働く。新しい課金形態を発明しない。

1. **RFQ差別化**: 状態説明機能を、RFQの診断・vehicle health・SOTIF関連要求への回答として提示する。効果は採否と価格交渉力に出る(機能単体の値札ではない)
2. **診断コンテンツNRE**: OEMがprogramごとに診断仕様の開発費を払う既存慣行に、payload仕様の設計・適合作業を乗せる
3. **将来のrecurring(仮説段階)**: vehicle health基盤へ部品側contributionを供給し続ける保守契約。ただしこれはOEM側の基盤成熟に依存するため、初期収益計画に入れない

## 何が競争優位か(3行で)

1. **観測点の独占**: EPSコネクタ点の電圧×アシスト状態×閾値未満eventの同時性は、EPS設計者以外は原理的に取れない
2. **言葉の設計**: 「原因断定なしで言える状態説明+機械的な禁止主張ガード」は、法務・品質リスクを恐れるOEMに対する提案の質の差になる(境界ガードはこのための資産)
3. **サプライヤ運用の実績**: 第2層(市場シグナル監視)を自分でやっている事実が、「この会社は市場の壊れ方を部品側から説明できる」という信用になる

## これは何でないか(既往Killとの整合確認)

- fleet監視サービスではない(docs/75でKill済み。買い手はfleetでなくOEM、形はサービスでなく製品仕様)
- OEM remote diagnostics説明レイヤーの外販ではない(archive済み。本モデルはサプライヤEPS製品に限定)
- SOTIFプロセス支援ではない(docs/126でNo-Go済み。SOTIFはRFQ要求への回答部品としてのみ触る)
- 故障予測商品ではない(Kill維持。売るのは説明能力であり予言ではない)
- 監視ツール外販ではない(第2層は内部投資。Viaduct等の既存市場に参入しない)

## ビジネスモデルのKill条件(技術のKillではなく、事業のKill)

| KQ | 質問 | Noの場合 |
|---|---|---|
| BM-KQ1 | OEMのRFQ/技術要求に、fault未満の状態説明・vehicle health contribution・in-service監視に類する要求が実際に現れているか(docs/126のKQ1と同一。内部資料条件) | 第1層は時期尚早。第2層(内部投資)だけ残し、要求が現れるまで製品仕様は棚に置く |
| BM-KQ2 | その要求は採点・選定に影響するか(「あれば加点」か「無償の当然要求」か) | **無償の当然要求ならこのモデルはKill**——機能はコストであって事業ではない。実装最小化に方針転換 |
| BM-KQ3 | 診断コンテンツNREの慣行に、payload設計を乗せる余地があるか | NREなしなら第1層の回収は採否・単価のみ=検証がより長期化する。継続判断を経営判断に上げる |
| BM-KQ4 | 社内品質・製品企画が第2層の監視レポート(docs/137の見本)を実際に使うか | 内部にすら使い手がいないなら、信用の裏付けが立たず第1層の営業トークが空になる。全体をHold |

BM-KQ1/2/3は内部資料条件(RFQの中身)。BM-KQ4は社内確認。**つまり事業の検証は技術の検証と違い、公開情報では閉じない。** ここが本Repoの正直な到達限界であり、docs/123と同じ「実施条件」として保存する。

## Rule Check

1. `Market Demand First`: OEMの誤診実費と監視義務という金銭的痛みから始めた
2. `Natural Language First`: 3層構造と金の流れを平文で先に定義した
3. `EPS Supplier Lens`: 売る/実施する/売らないを明記した
4. 既往Kill(fleet、remote diagnostics、SOTIF支援、故障予測)を再提案していないことを「これは何でないか」で確認した
5. Kill条件を技術でなく事業の言葉(採点影響、NRE余地、社内利用)で定義した
