# Predictive Value Continue Final Decision

> Correction: この文書の「公開情報とKaggle proxyだけで続ける調査アイテムは、ここで閉じる」という判断は強すぎた。
> EPS内部状態やDTC、freeze frame、交換結果が見えないことをKill理由の主因にしており、現行のKaggle / Public Proxy Predictive Value Ruleと矛盾する。
> 最新判断は [docs/96_predictive_value_internal_fact_correction.md](96_predictive_value_internal_fact_correction.md) を参照する。
> 修正後は、`PVC001`、`ULC008`、`ULC004`、`PVC004` を、外販商品ではなく公開proxy価値の検証候補として残す。

## 結論

公開情報とKaggle proxyだけで続ける調査アイテムは、ここで閉じる。

一番残りそうだったのは、車両がEPSにとって厳しい使われ方に入りやすいかを先に分類する方向だった。
具体的には、駐車場で低速・大舵角・凹凸が重なる使われ方や、荒れた路面で操舵入力が重なる使われ方である。

ただし、これは現時点では外販商品にならない。
公開proxyでは、EPS内部状態、DTC、freeze frame、extended data、assist state、limit state、motor current、temperature、交換結果、再発有無、既存診断や既存評価との差分が見えない。
そのため、EPSサプライヤが「予測のような付加価値」として売れるところまでは証明できない。

残すものは、商品候補ではなくサプライヤ内レビュー材料である。

1. 駐車場、低速、大舵角、凹凸が重なる使われ方を、製品企画と診断企画に見せる材料
2. 荒れた路面と操舵入力が重なる使われ方を、品質改善、評価企画、顧客技術説明に見せる材料
3. 通信異常時にEPS故障と誤認しないための、診断信頼性と禁止主張の境界材料

これらも、現在の公開情報調査としては追加深掘りしない。
サプライヤ内レビューで既存業務との差分が出た場合だけ再開する。

ID別の最終判断表は [data/predictive_value_continue_final_decisions.tsv](../data/predictive_value_continue_final_decisions.tsv) に置く。

## 何を判断しているか

判断しているのは、Kaggleや公開データからEPSの故障、残寿命、交換時期を当てられるかではない。
それはこのRepoでは禁止主張に置いている。

判断しているのは、公開proxyから見える速度、操舵要求、stop-start、路面・振動、交通状態、通信異常を、EPSサプライヤの業務成果物に変換できるかである。

業務成果物とは、製品企画の用途別価値説明、診断企画の使用context説明、品質改善のfield issue整理、評価企画の代表性確認、顧客技術説明の禁止主張整理である。

今回の結論は、その変換が「あり得る」までは見えたが、「売れる」までは行かない、である。

## 市場需要

低速取り回し、駐車操作、荒れた路面、段差、stop-start、操舵感、音、振動、違和感は、ユーザやサービス現場にとって分かりやすい困りごとになりやすい。

EPSサプライヤ側でも、こうした困りごとをすぐに故障原因や寿命へ飛ばさず、使われ方のclassとして整理したい需要はあり得る。
製品企画、診断企画、品質改善、評価企画が同じ言葉で使われ方を議論できれば、用途別の説明や診断境界の整理には役立つ可能性がある。

## 未解決の痛み

痛みはあるが、公開proxyだけでは核心に届かない。

公開proxyで見えるのは、低速、大舵角、操舵頻度、路面・振動、stop-start、交通状態、通信異常のような周辺contextである。

見えないのは、EPS内部で何が起きたかである。
DTC、freeze frame、extended data、assist state、limit state、motor current、temperature、software/calibration ID、交換結果、再発有無、既存診断で既に説明できているかは見えない。

この差を無理につなぐと、故障予測、原因断定、保証判断、安全保証に見えてしまう。
それはEPSサプライヤとして言ってはいけない。

## 仮説

検証した仮説は、公開proxyから「厳しい使われ方に入りやすいclass」を先読みできれば、EPSサプライヤの価値になるのではないか、である。

ただし、価値の置き方は限定した。

個車のEPSがいつ壊れるかを当てるのではない。
駐車場、低速、大舵角、凹凸、荒れた路面、通信異常のようなcontextを先に分類し、製品企画、診断企画、品質改善、評価企画が既存業務の見方を少し変えられるかを見る、という仮説である。

## 解決策候補

作れるものは、外販サービスではなくサプライヤ内レビュー用の小さな材料である。

1. `ULC008` の製品企画向け1枚
2. `ULC008` の診断企画向け1枚
3. `ULC004` の品質改善・評価企画・顧客技術説明向け1枚
4. `PVC004` の通信異常時の診断信頼性境界表

これらは、公開proxyで見えること、見えないこと、言ってよいこと、言ってはいけないことを同じ画面に置くための材料である。

## 買い手 / 利用者

外部の買い手は、現時点では置かない。

初期利用者として置けるのは、EPSサプライヤ内の製品企画と診断企画である。
品質改善、評価企画、顧客技術説明、サイバー担当は二次利用者である。

ここで重要なのは、サプライヤ内利用者が「既存のカタログ、RFQ回答、DTC、freeze frame、評価scenario、CSMS/TARA資料では足りない」と言えるかである。
それが言えなければ、この方向は既存業務の言い換えで終わる。

## 検証方法

これ以上、公開Kaggle調査を増やしても、同じ限界に当たる可能性が高い。

次に確認するなら、外部調査ではなくサプライヤ内レビューである。
ただし、これは現行の公開情報調査の続きではなく、再開条件である。

確認する質問は4つでよい。

1. 製品企画は、`ULC008` を用途別のEPS価値説明に使えるか
2. 診断企画は、`ULC008` を既存DTC / freeze frame / extended dataでは粗い使用context説明に使えるか
3. 品質改善または評価企画は、`ULC004` を既存NVH、耐久、評価scenarioとは違う切り口として使えるか
4. 診断企画またはサイバー担当は、`PVC004` を通信異常時の診断信頼性境界として使えるか

この4問に具体的な使い道が出なければ、このブランチは完全Archiveでよい。

## Kill条件

この方向は、次のどれかに当たれば止める。

1. 既存カタログ、RFQ回答、DTC、freeze frame、評価scenario、CSMS/TARA資料で十分と言われる
2. 価値を説明するために、故障予測、交換時期予測、保証費削減、安全保証、原因断定へ寄せる必要がある
3. 製品企画と診断企画のどちらにも具体的な使い道がない
4. `ULC004` が既存NVH、耐久、路面評価の言い換えで終わる
5. `PVC004` が汎用IDS、CSMS、TARA、SOC運用の言い換えで終わる

## EPSサプライヤとしての結論

EPSサプライヤとして、現時点で売るものはない。

EPSサプライヤとして実施できるのは、公開proxyを使って、使用負荷classと診断信頼性境界のサプライヤ内レビュー材料を作るところまでである。
ただし、それを外販商品やSaaS、故障予測、交換時期予測にはしない。

EPSサプライヤとして言ってはいけないのは、公開proxyからEPS故障、残寿命、交換時期、保証費削減、安全性、root causeが分かるという主張である。
駐車操作、低速高操舵、荒れた路面、通信異常がEPS故障原因であるとも言ってはいけない。

OEM領域、fleet platform領域、service platform領域として初期対象外に置くものは、車両全体の運行可否、保証DB連携、fleet downtime最適化、remote diagnostics platform、汎用IDS、CSMS/TARA運用である。

次に見せるなら、製品企画と診断企画である。
ただし、それは新しい調査の開始ではなく、このブランチを完全に閉じるか、サプライヤ内限定で再開するかを見る最終確認である。
