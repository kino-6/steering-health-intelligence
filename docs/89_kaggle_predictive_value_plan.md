# Kaggle予測的付加価値 探索計画

## 結論

現時点で最初に深掘りするべきなのは、EPSがいつ壊れるかではなく、どの用途や走り方がEPSにとって高負荷な使われ方になりそうかを先に分類する方向である。

この方向を `PVC001` として扱う。
自然言語では「使用負荷classの先読み」である。

次点は、操舵要求と路面・振動が重なる条件を先読みする方向である。
これは `PVC002` として扱う。

通信異常contextは、外販商品ではなく、EPS故障と誤認してはいけない異常contextを先に分ける守りの価値として残す。
これは `PVC004` として扱う。

KGL001の製造・EOL検査、KGL002の評価時間予測は、予測という意味では分かりやすいが、今回の「実使用からEPS付加価値を探す」本線とは別枝に置く。

## 何を判断しているか

判断しているのは、KaggleでEPS故障予測ができるかではない。
判断しているのは、公開proxyから見える運転行動、操舵要求、路面・振動、交通状態、通信異常が、EPSサプライヤにとって先読み価値に変わるかである。

先読み価値とは、以下のどれかに転記できることである。

1. EPS製品企画で、用途ごとの要求や価値説明に使える
2. 診断企画で、DTCやfreeze frameだけでは見えにくい使用contextを説明できる
3. 品質改善で、field issueを使用条件別に読み直す入口になる
4. 評価企画で、既存評価がどのusage classを代表しているかを確認できる
5. 顧客技術説明で、故障原因を断定せず、使用条件の可能性を説明できる

評価scenarioや診断質問を作ること自体は主目的ではない。
それらは、先読み価値が本当に業務価値へ落ちるかを確認するための副次artifactである。

## 実施順

### Phase 1: 候補ID化

KGL003〜KGL012とUF001〜UF030を、予測的付加価値候補へ変換する。
成果物は [data/kaggle_predictive_value_candidates.tsv](../data/kaggle_predictive_value_candidates.tsv) である。

受け入れ条件:

- 各候補が「何を先読みするのか」を自然言語で説明している
- 買い手または利用者がEPSサプライヤ内の部署として書かれている
- 言ってはいけない主張が明記されている
- Proceed / Hold / Killの現時点判断がある

### Phase 2: PVC001を深掘り

最初に、使用負荷classの先読みを深掘りする。
これは、低速高操舵、据え切りに近い操舵、stop-start、荒れた路面、反復操舵、駐車場走行などを束ね、EPSに厳しい使われ方を分類する仮説である。

成果物は [docs/90_pvc001_usage_load_class_deep_dive.md](90_pvc001_usage_load_class_deep_dive.md) と [data/pvc001_usage_load_class_sample.tsv](../data/pvc001_usage_load_class_sample.tsv) である。

受け入れ条件:

- 使用負荷classを5〜10件に絞る
- 各classについて、公開proxy、使う部署、価値、禁止主張、Kill条件を書く
- 「EPS故障予測」ではなく「使用負荷classの先読み」として説明できる

### Phase 3: PVC002 / PVC003を深掘り

PVC001が残る場合だけ、操舵要求 x 路面・振動exposureと、都市/駐車場低速高操舵profileを深掘りする。
PVC001と重複が強い場合は、PVC002 / PVC003を独立テーマにせず、PVC001のsub-classに統合する。

受け入れ条件:

- PVC001と異なる買い手または意思決定がある
- 独立した価値がなければ統合する
- 路面分類や操舵角推定をそのまま商品にしない

### Phase 4: PVC004を境界確認として整理

通信異常contextは、EPS health商品ではなく、診断信頼性と禁止主張の境界として扱う。
KGL004 / KGL011を使い、CAN DoS、spoofing、fuzzy attackがある場合に、EPS故障と誤認しないための説明境界を作る。

受け入れ条件:

- 汎用cyber商品にしない
- SbW安全証明に使わない
- EPSサプライヤが言えることと言ってはいけないことを分ける

### Phase 5: Kill判定

最後に、候補ごとに以下を確認する。

- 市場需要から始まっているか
- EPSサプライヤの部署に転記できるか
- 既存評価・診断・品質業務との差分があるか
- OEM保証DB、fleet data、service outcomeに過度依存していないか
- 故障予測、交換時期、安全保証、保証費削減を言い始めていないか

## EPSサプライヤとしての言い方

言ってよいこと:

> 公開proxyだけではEPS内部状態や残寿命は分からない。一方で、操舵要求、路面・振動、交通状態、運転行動を組み合わせると、EPSに厳しい使われ方のclassを先に読む余地はある。このclassが製品企画、診断企画、品質改善、評価企画に転記できるかを検証する。

まだ言ってはいけないこと:

> EPS故障を予測できる。

> EPS交換時期を推定できる。

> 公開proxyからEPS内部stress、thermal limit、assist limitation、DTC不足を断定できる。

> Kaggle datasetを使えば保証費削減や安全保証ができる。

## 次アクション

まずPVC001を深掘りし、使用負荷classを5〜10件に絞る。
そこで、EPSサプライヤ内の製品企画、診断企画、品質改善、評価企画のどこにも転記できない場合は、このKaggle予測的付加価値探索は早めに止める。
