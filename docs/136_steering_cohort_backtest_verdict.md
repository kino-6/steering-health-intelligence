# Steering Cohort Backtest: Verdict

## 結論

フェーズD(時点区切りバックテスト)を実装した。問いは「[docs/135](135_steering_cohort_curve_demo_verdict.md) の群曲線は事後の答え合わせに過ぎないのではないか。**その時点で知り得た届出だけで、リコールの前に浮きは見えたか**」である。

答え: **見えた。しかも偽陽性ゼロで。**

| 年式cohort | 位置づけ | 検知ルール初回発火 | リコール公表(2015-07)より |
|---|---|---|---|
| MY2012 | リコール対象 | **2013-06-30** | **25ヶ月前**(ODI調査開始 2014年半ば より約1年前) |
| MY2011 | リコール対象 | 2014-12-31 | 7ヶ月前 |
| MY2010 | 調査対象(PE14-030) | 発火せず | -(下記「正直な負の結果」参照) |
| MY2013 | 比較対象(非リコール) | **発火せず(正しい陰性)** | - |
| MY2014 | 比較対象(非リコール) | **発火せず(正しい陰性)** | - |

検知ルールは実装前に固定した(後出し判定の排除):

> 操舵系届出30件以上(量の下限) かつ 操舵系比率が旧世代基準(MY2008-2009、油圧PS、計2,372件)の2倍以上 かつ 比率30%以上

- 実行: `python3 scripts/steering_cohort_backtest.py`(9つの半年刻みcutoff、2011-06〜2015-06)
- 出力: [generated/steering_cohort_backtest.html](../generated/steering_cohort_backtest.html) / [data/steering_cohort_backtest.tsv](../data/steering_cohort_backtest.tsv)

## 何を判断したか

需要マップ空席(2)「群レベルの故障傾向」が、記述(過去がこうだった)を超えて**早期検知(その時点で気づけた)**として機能するかである。docs/135 の限界6として自ら挙げた検証を実施した。

## 時点ごとの推移(届出ベースの操舵系比率)

```
cutoff      旧世代基準  MY2010  MY2011  MY2012   MY2013  MY2014
2012-12-31    6%        4%     24%     27%      -       -
2013-06-30    5%        5%     16%     34% ●    7%      -
2013-12-31    4%        4%     16%     43% ●    11%     (33%/n小=発火せず)
2014-06-30    3%        6%     22%     49% ●    11%     18%
2014-12-31    4%       11%     35% ●   58% ●    16%     14%
2015-06-30    4%       13%     42% ●   62% ●    17%     13%
```

●=ルール発火。量の下限(30件)が効いている点に注目:
MY2014は2013-12時点で33%を示したが件数が少なく発火しなかった。**小標本の偶然を量の下限が正しく抑えた**(その後14%へ回帰=偽陽性を防いだ)。

## 正直な負の結果: MY2010は発火しなかった

MY2010(PE14-030の調査対象)は、リコール公表前の比率が最大13%に留まり発火しなかった。
MY2010の操舵系苦情の大半(累積曲線でも確認済み)は**リコール報道後(2015年以降)に届出**されており、届出ベースの本ルールでは事前に見えない。

これが意味すること:

1. 本ルールは「症状を経験した所有者が届出する行動」に依存する。届出行動が遅いcohortは検知できない
2. つまり苦情ベースの群検知は**万能ではない**。部品内部の観測(空席(1)=SPD008 payload)と相補的である——内部観測は届出行動に依存しない。2つのDemoが別々の穴を埋めていることが、この負の結果で明確になった

## Rule Check

今回の判断では、[AGENTS.md](../AGENTS.md) の次を適用する。

1. `Market Demand First`: 「早く気づきたい」需要(品質改善・製品企画)への直接の回答である
2. `Natural Language First`: 結論を平文と表で先に示した
3. `EPS Supplier Lens`: EPSサプライヤがサプライヤ搭載車種について公開データで運用できる監視の実証。売り物ではなく内部業務の道具
4. `Kaggle / Public Proxy Predictive Value Rule`: 「MY2012 cohortに市場シグナルの偏りがあった」と言い、「個車が壊れる」「原因が確定した」とは言わない
5. 検知ルールの事前固定により、後出しの閾値調整を排除した
6. 負の結果(MY2010)を隠さず、手法の適用限界として記録した

## 限界(正直に)

1. **現在のDBの届出日が当時のまま保存されている前提**。取り下げ・遅延登録・重複は補正できない
2. 旧世代基準は油圧→EPASの技術変化を含む。2倍マージン+絶対下限30%で緩和しているが、完全には分離できない
3. **1車種系列・1事象での検証**。ルールの汎化(閾値の妥当性)は他車種への横展開で確認が要る
4. 発火が「何に」気づいたかは苦情本文を読まないと分からない(本テストは比率のみ。カテゴリ内の故障モード識別は次段階)
5. 25ヶ月のリードは最良ケース(MY2012)。MY2011は7ヶ月、MY2010は検知不能——リードは保証値ではない

## 目的地に対する現在地(フェーズA〜D完了)

> **故障予測の需要調査、および必要ならデータ収集、Demo構築。**

| フェーズ | 成果 |
|---|---|
| A 需要マップ | 買い手6セグメント、空席2つを特定(docs/133) |
| B データ当たり付け | 公開データでGo判定(docs/134) |
| C Demo v2 | 群曲線、事後の答え合わせ成功(docs/135) |
| D バックテスト | **事前検知25ヶ月/7ヶ月、偽陽性ゼロ、負の結果も記録**(本ドキュメント) |

需要調査の最終回答として言えること:

> 個車の故障予測は売れない(席がない+禁止主張)。しかしEPSサプライヤは、(1)部品内部のDTC未満観測(SPD008 payload)と、(2)公開データの群レベル早期検知(本Demo)という**2つの相補的な「予測のような付加価値」**を、内部データなし・禁止主張なしで実証できる状態にある。(1)は届出行動に依存せず、(2)は実装を要しない——互いの弱点を埋め合う。
