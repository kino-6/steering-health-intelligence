# LLM向けKill知識ベース

## 目的

この文書は、人間向けの探索レポートではない。
次にこのRepoを読むLLMが、過去に潰した仮説をもう一度もっともらしく提案しないための前提知識である。

このRepoでは、以下の制約が強い。

- EPSサプライヤ視点に戻す
- 内部資料を使わない
- OEM保証DB、fleet data、サービス領域を初期前提にしない
- 既存診断、既存安全設計、既存品質業務の言い換えを新規価値と呼ばない
- 公開情報だけで、買い手、利用者、解決策、Kill条件まで自然言語で説明する

この制約のままでは、外販ビジネスとして強い手札はほぼ残っていない。
現時点で最も重要な成果は、有望案ではなく **Killの蓄積** である。

## LLMが最初に守ること

新しい提案を出す前に、必ず次を確認する。

1. 市場変化と購買需要を分ける
2. 既存業務の持ち主がいないか確認する
3. EPSサプライヤが部品境界で言えることに限定する
4. OEM領域、fleet領域、サービス領域へ逃げない
5. 公開情報だけで対象EPSの不足を断定しない
6. 追加ログ、故障予測、保証費削減を主張しない
7. 商品名や英語略語を先に出さない
8. Kill条件を必ず書く

悪い出力:

> Steer-by-wire向けEvidence Packを売れる。

良い出力:

> Steer-by-wireでは異常時説明が重要になる。ただし、安全設計、認証、診断設計、ソフト更新、顧客技術説明には既に持ち主がいる。公開情報だけでは未解決の購買需要を示せないため、汎用外販はNo-Go。残すなら、特定案件で既存資料をOEM向け1枚へつなぐ短期支援だけである。

## 現行結論

現行条件では、外販ビジネスとしてProceedできる案はない。

> Trust recovery correction:
> この文書のKaggleに関する記述は、後続レビューで補正された。
> Kaggle / Public Proxy系では、EPS内部状態、DTC、freeze frame、交換結果が見えないことを主Kill理由にしてはいけない。
> 最新判断は [docs/96_predictive_value_internal_fact_correction.md](96_predictive_value_internal_fact_correction.md) と [docs/97_trust_recovery_rule_check_audit.md](97_trust_recovery_rule_check_audit.md) を参照する。
> 修正後は、`PVC001`、`ULC008`、`ULC004`、`PVC004` を公開proxy価値の検証候補として残す。

残る可能性は、次のどちらかだけである。

1. 内部資料を使える条件に変わった場合の再開
2. 外販商品ではなく、特定案件やサプライヤ内向けの短期整理支援

それ以外の公開情報ベースの探索は、かなりの確率で「事例紹介」「既存業務の言い換え」「買い手不明」に戻る。

旧テーマはArchive扱いにする。
ここでいう旧テーマは、乗用車向けEPS単体について、公開情報だけを使い、故障予測、劣化兆候通知、追加ログ、公開市場pain分類、Coverage Benchmark、汎用SbW説明支援、SOVD基盤支援を外販商材にできるかを探した一連の探索である。

新しく見る場合は、EPS単体の寿命予測ではなく、自動運転車両、配送車、商用車、シャトルなどの車両群で、操舵系を含む重要部品について、次の運行に出してよいか、次回点検まで持つか、先に入庫させるべきかを判断できるかに絞る。
最初に確認するのは、操舵系理由の運行停止・予定外入庫が本当に痛いか、EPS / SbWサプライヤが必要データにアクセスできるか、既存DTCや通常診断だけでは業務判断に不足するかである。
この入口は [docs/69_old_theme_archive_and_new_focus.md](archive/motion_health/69_old_theme_archive_and_new_focus.md) と [data/motion_health_new_focus_questions.tsv](../data/archive/motion_health/motion_health_new_focus_questions.tsv) に置く。

Kaggleコンペは、需要調査の枝としてだけ再確認してよい。
ただし、Repoの主仮説にはしない。
Bosch型の製造不良予測とMercedes-Benz型の評価時間短縮は、EPSサプライヤが持てる製造、EOL検査、bench/HILS評価データに近い。
しかしこれは製造品質、検査工程、評価運用の話であり、EPS製品そのものの付加価値ではない。
本題に戻る場合は、EPS製品仕様、診断仕様、制御仕様、評価仕様、OEM説明に残る価値だけを主探索にする。

## Kaggleについての例外ルール

Kaggleを使う場合、次のように扱う。

| 見方 | 判断 |
|---|---|
| EPS市場故障予測用データ | 使わない。DTC、freeze frame、assist電流、motor電流、limit状態、返却品判定、保証ラベルが足りない |
| 公開CAN/OBD/steering angleデータ | 使用条件proxyにはなるが、EPS故障や診断不足の証明には使わない |
| Kaggleコンペの課題設定 | 使ってよい。企業が外に出した目的変数を、隠れた業務需要として読む |
| Bosch Production Line Performance | 製造品質、工程検査、EOL検査の需要シグナルとして残す |
| Mercedes-Benz Greener Manufacturing | 評価時間、bench/HILS/EOL検査時間短縮の需要シグナルとして残す |

Kaggleから復活してよい仮説は、次だけである。

> EPSサプライヤが自分で持てる製造、工程検査、最終検査、EOL検査、bench/HILS評価データを使い、不良候補、再試験候補、評価時間、試験優先順位を出せるか。

これは、故障予測ではない。
市場に出た車の残寿命を当てる話でもない。
サプライヤ内部の製造品質と評価効率を上げる話である。

Kill条件:

- ただのKaggle精度競争で終わる
- EPSサプライヤの工程、検査、評価計画に転記できない
- 既存SPC、BI、品質管理、工程改善で十分
- OEM保証DBやfleet dataを前提に戻る
- EPS故障予測や劣化兆候通知を主張し始める
- EPS製品価値探索の主仮説として扱い始める

## よくある誤った復活パターン

### 1. 市場で話題だから売れる

市場変化があることと、EPSサプライヤが外部サービスを買うことは別である。
量産化、規制、標準化、公開発表は、市場需要の証拠にはなる。
しかし、購買需要の証拠にはならない。

### 2. 既存資料を束ねれば価値になる

束ねるだけでは価値にならない。
既存成果物の持ち主がいて、既存会議や既存帳票で十分ならKillである。
価値が残るのは、部署横断で毎回つなぎ直しが発生し、OEM向け説明や設計レビューに貼れる場合だけである。

### 3. 診断情報を増やせば価値になる

診断情報の追加は、利用先がない限り価値ではない。
DTC、freeze frame、extended dataで既に十分ならKillである。
不足を主張するには、対象EPSの既存診断仕様が必要だが、現行方針では内部資料を使わない。

### 4. 故障予測に戻る

このRepoでは、EPSサプライヤ単独の故障予測や劣化兆候通知は主張しない。
外部要因、OEMデータ、fleet data、保証ラベルが必要になるためである。

### 5. OEM領域へ逃げる

OEM保証DB、fleet analytics、サービスツール、車両クラウド、認証代行を初期前提にしない。
これらを前提にすると、EPSサプライヤ視点から外れる。

## 現行条件で残るもの

外販商品ではないが、以下は残してよい。

| 残すもの | 使い方 | 注意 |
|---|---|---|
| 公開EPS pain family分類 | 市場で繰り返す困りごとの入力 | 単体では売らない |
| 公開recall / ODI / TSB / 規制 / 標準モニタ | 設計質問、診断質問、禁止主張の入力 | ニュース整理で終わらせない |
| 1ケースの説明1枚 | 既存資料の要約を超えるかを見る判断材料 | 商品名を付けない |
| Kill条件リスト | LLMが無理筋を再提案しないための前提 | Proceed条件と混ぜない |
| 内部資料を使える場合の再開条件 | 将来の探索再開条件 | 現行アクションにしない |

## 前提を変えるなら復活する可能性があるもの

| 前提変更 | 復活候補 | 理由 |
|---|---|---|
| 内部資料を少し使える | Coverage Benchmark、既存資料横断整理 | 既存HILS/DTC/freeze frame/reviewとの差分を見られる |
| OEM / fleet / service領域を許す | 故障予測、予兆通知、市場品質モニタ | 個車データ、保証ラベル、サービス判断へ接続できる |
| 特定案件の支援に限定する | RCA/8D、SbW説明1枚、cyber/SBOM回答支援 | スケールより案件処理価値を優先できる |
| EPSサプライヤではなく調査会社視点にする | 公開市場モニタ、規制/標準ウォッチ | 公開情報整理そのものが商品になり得る |
| LLMサプライヤ内ナレッジ化に寄せる | Kill知識ベース、質問生成、レビュー補助 | 外販ではなく意思決定支援として価値がある |
| 公開データをKaggleコンペの課題設定として読む | 製造不良予測、評価時間短縮 | 企業が目的変数を設定しており、サプライヤ所有データに寄せやすい |

## LLMへの判断ルール

新しい案を出す場合、次のいずれかを満たさないなら提案しない。

1. 公開情報だけで購買需要まで示せる
2. 既存業務の持ち主との差分を自然言語で説明できる
3. EPSサプライヤが部品境界で実施できる
4. OEM/fleet/service領域に依存しない
5. Kill条件が具体的で、Stopできる

満たせない場合は、次のように答える。

> 現行条件では外販ビジネスとしては弱い。前提を変えるなら、内部資料を使う、OEM/fleet領域を許す、または特定案件支援に限定する必要がある。

## 最終メモ

このRepoの現行条件では、強い外販商材をさらに探すより、Kill知識を前提にして、前提変更があった時だけ探索を再開する方がよい。

次のLLMは、まずこの文書を読み、過去にKillした仮説を「言い換え」で復活させないこと。
