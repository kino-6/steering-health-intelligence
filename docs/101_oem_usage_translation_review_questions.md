# OEM Usage Translation Review Questions

## 結論

次に確認することは、公開proxyからEPS故障を当てられるかではない。
OEMが想定する使われ方を受け取ったときに、EPSサプライヤの各部署が、自分たちの既存成果物へ貼れる具体的な質問、説明境界、禁止主張を出せるかである。

最初に見せる相手は、製品企画と診断企画である。
この2部署で具体用途が出なければ、品質改善、評価企画、サイバー担当へ広げても本線は弱い。

質問票の作業表は [data/oem_usage_translation_review_questions.tsv](../data/oem_usage_translation_review_questions.tsv) に置く。

## 何を判断しているか

判断しているのは、次である。

> OEM用途想定を、EPSサプライヤ側の製品説明、RFQ確認、診断説明、品質改善、評価確認、顧客技術説明へ翻訳できるか。

これは、駐車場や荒れた路面を新しい有望用途として発見する作業ではない。
それらはOEMの用途想定に含まれうる既知の使われ方である。

EPSサプライヤ側で見るべきことは、その用途想定を受けて、既存カタログ、既存RFQ回答、既存DTC / freeze frame / extended data、既存評価項目、既存顧客説明と違う確認観点が出るかである。

## 市場需要

低速取り回し、反復操舵、大舵角、段差、荒れた路面、通信異常は、ユーザやサービス現場に見えやすい。
OEMはこれらを、車両コンセプト、用途想定、評価条件、サービス説明へ落とす必要がある。

EPSサプライヤに残る需要は、OEMの用途想定を受けたときに、EPS側で確認すべきこと、説明してよいこと、説明してはいけないことを短く返せることである。

## 未解決の痛み

公開proxyやKaggleの問題設定は、低速、操舵、路面、振動、通信異常を示せる。
しかし、そのまま使うと、一般的な運転行動分析、路面分類、ADAS、汎用IDSに見える。

未解決なのは、proxyの量ではない。
それをEPSサプライヤの既存業務へ貼れる形に変換できるかである。

## Rule Check

今回の質問票では、[AGENTS.md](../AGENTS.md) の次を適用する。

1. `Market Demand First`
2. `Natural Language First`
3. `EPS Supplier Lens`
4. `Kaggle / Public Proxy Predictive Value Rule`
5. `OEM Usage Translation Rule`
6. `Mandatory Rule Check Before Stop / Kill / Archive`

この文書では、最終的なStopやArchiveを出していない。
ただし、質問ごとに止める条件を書くため、次を守る。

- EPS内部状態、DTC、freeze frame、交換結果が見えないことだけを止める理由にしない
- 公開proxyを、EPS故障原因、残寿命、交換時期、安全保証の代替にしない
- OEMの車両コンセプトを、EPSサプライヤが公開proxyだけで定義できるとは言わない
- 汎用テレマティクス、路面分類、ADAS、IDSと区別できるかを聞く
- 判断を、EPSサプライヤの業務成果物へ転記できるかに置く

## レビューの進め方

最初の30分では、4枚すべてを議論しない。
製品企画と診断企画だけに絞る。

1. 製品企画に、OEM用途想定をEPS価値説明とRFQ質問へ変換できるか聞く
2. 診断企画に、同じ用途想定を使用context説明の境界へ変換できるか聞く
3. どちらかで具体用途が出た場合だけ、品質改善 / 評価企画へ広げる
4. 通信異常の話は、診断企画で必要性が出た場合だけサイバー担当へ広げる

## 製品企画へ聞くこと

最初に聞く質問:

> OEMが低速、反復操舵、大舵角、段差、路面外乱を含む用途を想定しているとき、既存カタログや既存RFQ回答にはないEPS側の確認質問は何か。

この質問で見たいのは、故障しにくさの主張ではない。
低速取り回し、操舵感、路面外乱下の体感、電源、温度、通信条件を、製品価値やRFQ確認へ翻訳できるかである。

進めてよいサイン:

- 既存RFQ回答にない確認質問が出る
- 故障予測や保証費削減を言わずに、EPS製品価値として説明できる
- 次に確認したいOEM用途、車格、サービス、運行シーンが具体化する

弱いサイン:

- 既存カタログの言い換えで終わる
- 価値説明に、壊れにくさ、残寿命、交換時期が必要になる
- OEMの用途コンセプトを代わりに定義する話になる

## 診断企画へ聞くこと

最初に聞く質問:

> OEM用途想定に低速反復操舵や路面外乱が含まれるとき、既存DTC / freeze frame / extended dataだけで使用contextをどこまで説明できるか。

この質問で見たいのは、DTCを増やすことではない。
既存診断結果を読むときに、使用contextとして説明してよい範囲と、説明してはいけない範囲を分けられるかである。

進めてよいサイン:

- 既存診断値だけでは使用context説明が粗いと言える
- 診断読み順、追加確認項目、顧客説明境界へ転記できる
- 原因断定ではなく、説明の限界線として使える

弱いサイン:

- 既存診断で十分に説明できる
- 顧客説明に使うと責任転嫁や原因断定に見える
- 価値説明がDTC追加、故障予測、保証判断へ流れる

## 品質改善 / 評価企画へ聞くこと

製品企画または診断企画で具体用途が出た場合に聞く。

最初に聞く質問:

> OEM用途想定に荒れた路面、段差、連続振動、操舵入力が含まれるとき、既存NVH、耐久、路面評価とは違う確認観点が出るか。

この質問で見たいのは、路面分類productではない。
field issueを使用条件別に読み直せるか、既存評価で足りる条件と追加確認すべき条件を分けられるかである。

進めてよいサイン:

- 品質改善がfield issueを使用条件別に読み直せる
- 評価企画が既存評価で足りる条件と足りない条件を分けられる
- 顧客技術説明で、路面外乱由来の体感とEPS異常を混同しない境界に使える

弱いサイン:

- 既存NVH、耐久、路面評価scenarioの言い換えで終わる
- 路面分類や車両全体NVHの話になる
- 荒れた路面がEPS故障原因であるように読まれる

## 診断企画 / サイバー担当へ聞くこと

通信異常contextは、最初から汎用サイバー商品として扱わない。
診断企画で「通信異常時に診断値やsignalの信用境界が必要」という反応が出た場合にだけ広げる。

最初に聞く質問:

> 通信異常があるとき、EPS診断値や操舵関連signalをどこまで信用してよいかを、診断企画とサイバー担当の間で分ける必要があるか。

進めてよいサイン:

- 通信異常時のDTC / freeze frame / signalの信用境界が必要と言える
- 既存CSMS / TARA / SOC / IDSと、EPS診断説明の境界を分けられる
- 顧客技術説明で、通信異常とEPS故障を混同しない禁止主張に使える

弱いサイン:

- 汎用IDS、CSMS、TARA、SOC運用の言い換えで終わる
- EPS診断説明や診断読み順に転記できない
- SbW安全証明、EPS品質証拠、steering cyber productとして扱いたくなる

## 判定

現時点で進めるべき最小判定は、次である。

Proceed:

- 製品企画と診断企画の少なくとも一方が、既存成果物に貼れる具体用途を出す
- 故障予測、交換時期、保証費削減、原因断定を言わずに価値説明できる
- 汎用テレマティクス、路面分類、ADAS、IDSと違うEPSサプライヤ側の成果物が見える

Hold:

- 使い道はありそうだが、既存RFQ、既存診断、既存評価との違いがまだ曖昧
- 具体programやOEM用途想定がないと、質問が一般論で止まる

Stop候補:

- どの部署も、既存成果物に貼れる具体用途を出せない
- 既存カタログ、既存RFQ回答、既存DTC説明、既存NVH/耐久評価の言い換えで終わる
- 価値説明に、故障予測、交換時期、保証費削減、root cause断定が必要になる

Stop候補と書く場合も、最終Stopではない。
最終判断では、上位ルールに沿ったRule Checkを改めて書く。

## EPSサプライヤとしての言い方

言ってよいこと:

> OEMの用途想定を受けたときに、低速反復操舵、路面外乱、通信異常のような観点を、EPSサプライヤ側のRFQ確認、診断説明境界、品質改善、評価確認、顧客技術説明へ翻訳できるかを確認する。

まだ言ってはいけないこと:

> 公開proxyからEPS故障、残寿命、交換時期、安全性、保証費削減、root causeが分かる。

> 駐車操作、荒れた路面、通信異常がEPS故障原因である。

> EPSサプライヤが公開proxyだけでOEMの用途コンセプトを定義できる。
