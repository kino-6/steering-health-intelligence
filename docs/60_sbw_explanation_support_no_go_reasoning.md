# Steer-by-wire説明資料整理支援のNo-Go理由

## 結論

ここで判断しているのは、次の仕事をEPSサプライヤ向けの有償サービスとして売れるかである。

> 機械的なつながりをなくす操舵について、異常時に車がどう動き、運転者に何が表示され、診断で何が読め、サプライヤが何を説明できるかを整理する仕事。

結論は、**現時点では有償サービスとしてはNo-Go** である。

理由は、市場変化はあるが、支払いが発生するほどの未解決の痛みが公開情報から見えないためである。
むしろ公開情報を見るほど、この仕事は既存の安全設計、認証、診断設計、ソフト更新、顧客技術説明の中に既に含まれているように見える。

つまり、需要がないのではない。
需要はある。
ただし、それは「新しい外部サービスを買いたい需要」ではなく、steer-by-wireを開発・認証・量産するなら当然やるべき既存業務の需要に見える。

EPSサプライヤとして残せるのは、外販商材ではなく、社内または案件内で使う説明整理である。

> 車輪を動かす側の部品に異常が起きた時、サプライヤが言えること / 言ってはいけないことを、設計・安全・診断・顧客技術窓口が同じ言葉で確認する。

この整理が既存資料からすぐ出るなら、この方向は止める。
既存資料はあるが、部署をまたぐ説明に毎回詰まる場合だけ、短期の案件支援として残す。

## 市場需要

市場で起きている変化は明確である。
ハンドルと車輪の間にあった機械的なつながりをなくし、信号とモータで車輪を動かす操舵が量産へ進んでいる。

公開情報では、ZFがMercedes-Benzへ2026年からsteer-by-wireを供給すると説明している。
Bosch、Nexteer、Schaeffler、HELLAなども、ハンドル側、車輪側、センサ、ソフト、冗長電源や通信といった部品や技術を説明している。

ここから言える市場需要は次である。

- steer-by-wireでは、異常時に残る操舵能力を説明する必要がある
- 機械的なつながりがないため、運転者への警告や制限動作の説明が重要になる
- 車輪を動かす側の部品、センサ、電源、通信、ソフトが安全や診断の中心論点になる
- OEM、認証機関、サプライヤ間で説明すべき文書や根拠が増える

ここまでは筋がよい。

## 未解決の痛み

ただし、ここで見えている痛みは、まだ「外から買いたい痛み」ではない。

公開情報から見えるのは、以下のような既存業務である。

| 業務 | 公開情報から見えること | 意味 |
|---|---|---|
| 安全設計 | NHTSAはsteer-by-wireの機能安全評価、危険分析、故障時状態、安全要求を扱っている | 異常時にどう安全側へ落とすかは既存論点 |
| 認証・承認 | VCAはR79の文書、故障時の考え方、検証、安全分析を説明している | 認証向けの説明資料は既存業務 |
| 診断設計 | NHTSAはDTC coverageを扱い、ASAM SOVDは故障情報やデータアクセスを扱っている | 診断で何を見せるかも既存論点 |
| 顧客説明 | サプライヤ公開資料は冗長性や高可用性を説明している | OEM説明は既に営業・技術活動の一部 |

したがって、未解決の痛みがあるとすれば、次のような狭いものに限られる。

> 既存資料はあるが、設計、安全、診断、ソフト、顧客技術窓口の資料が分かれていて、OEMへ短く説明する時に毎回つなぎ直しが必要になる。

これはあり得る。
しかし公開情報だけでは、それが実際に困っているか、予算がつくかは言えない。

## 仮説

最初の仮説はこうだった。

> steer-by-wireでは、従来EPSより説明責任が重くなる。だから、異常時状態、診断情報、冗長性、安全・認証根拠を束ねた説明資料を作れば、EPSサプライヤ向けに売れるのではないか。

検証後の仮説はかなり小さくなる。

> 売れる可能性があるのは、汎用の安全・認証・診断支援ではない。既存資料を、顧客説明や設計レビューに貼れる1枚へ翻訳する短期支援だけである。それも、既存の安全資料や顧客回答から同じものがすぐ出るなら止める。

## なぜ外販商材として弱いか

理由は5つある。

### 1. 市場需要と購買需要が違う

steer-by-wireが増えることは市場需要である。
しかし、それだけでは「外部から説明資料整理を買う」理由にならない。

量産開発をしているサプライヤなら、安全設計、診断設計、認証対応、OEM説明は既に業務として持っている可能性が高い。
この場合、外部サービスは新規価値ではなく、既存業務の言い換えになる。

### 2. 成果物の持ち主が既にいる

異常時の説明には、既に持ち主がいる。

- 安全設計は、安全要求や故障時の考え方を持つ
- 診断設計は、DTCや読み出し項目を持つ
- ソフト担当は、ソフト番号や更新後確認を持つ
- 顧客技術窓口は、OEMへの説明文を持つ
- 認証担当は、規制向けの文書を持つ

この人たちの成果物を置き換える提案にすると、かなり筋が悪い。
残るなら、置き換えではなく、既存成果物をつなぐ薄い支援である。

### 3. EPSサプライヤの責任範囲が限定される

EPSサプライヤが説明できるのは、部品境界内の事実である。

言えること:

- 部品がどの異常を検知したか
- どの制限動作に入ったか
- 診断で何が読めるか
- ソフトや設定値のどの版か
- サプライヤとして確認済みの範囲はどこか

言えないこと:

- 車両全体が安全である
- 認証を満たしている
- OEMの故障対応が十分である
- 根本原因がこれである
- 保証費が下がる

つまり、売れる範囲はどうしても狭い。

### 4. 公開情報だけでは差分を証明できない

公開情報からは、市場変化と既存論点は見える。
しかし、対象サプライヤの既存資料に同じ説明があるかは分からない。

このRepoでは内部資料を使わない方針なので、差分確認には進めない。
差分を確認できない以上、「外販できる」とは言えない。

### 5. スケールしにくい

もし価値があるとしても、案件ごとの部品構成、OEM要求、診断仕様、ソフト更新手順、安全分析に依存する。

そのため、SaaSや標準商品にしにくい。
成立するとしても、特定案件の短期支援、または社内向け説明テンプレートである。

## 解決策

現時点で作ってよいのは、商品ではない。
作るなら、次のような判断用の1枚である。

| 項目 | 中身 |
|---|---|
| 何が起きたか | 車輪を動かす側の冗長系が一部落ちた |
| 車はどう動くか | 残る経路で操舵を続ける、または低速退避などに制限する |
| 運転者には何が見えるか | 警告、音、退避要求、出力制限 |
| 診断で何が読めるか | 異常経路、発生時条件、電源/通信/温度/ソフト版など |
| サプライヤが言えること | 部品境界内で検知した事実と制限動作 |
| 言ってはいけないこと | 根本原因、車両全体の安全認証、保証費削減、故障予測 |

この1枚が既存資料の要約にしかならないならStop。
逆に、部署間の説明を明らかにつなぐなら、短期支援としてのみ残す。

## 買い手 / 利用者

買い手はまだ確認できない。

利用者候補は以下である。

- システム設計
- 安全設計
- 診断設計
- ソフト / キャリブレーション担当
- 顧客技術窓口
- 営業技術

ただし、これは買い手ではなく利用者候補である。
公開情報だけで予算持ちを断定しない。

## 初期提供物

初期提供物は商材ではなく、判断資料に留める。

1. 異常時説明1枚
2. 言えること / 言ってはいけないこと一覧
3. 既存業務との重複判定表
4. Stop条件

## 検証方法

内部資料を使わない方針では、検証は次に限る。

- 公開情報だけで、説明の形を作れるか
- 既存安全・認証・診断資料の要約を超えるか
- EPSサプライヤの責任範囲が明確になるか
- 買い手を断定せず、利用者候補に留められているか

検証しないこと:

- 対象EPSのDTC不足
- 対象EPSの安全分析不足
- 対象OEMのRFQ不足
- 顧客回答テンプレート不足

## Kill条件

以下のどれかに当たれば止める。

- 既存の安全資料、認証資料、診断資料の要約にしかならない
- EPSサプライヤの責任範囲が狭すぎて、OEM説明の中心になれない
- 利用者候補の業務成果物に貼れない
- 公開情報だけでは、診断で何を読めるかを説明できない
- 予算を持つ買い手が公開情報から見えない

## 最終判断

EPSサプライヤとして言えること:

> steer-by-wireでは、異常時の説明が安全、認証、診断、ソフト、顧客技術説明をまたぐ。公開情報だけでも、この横断説明の形は作れる。

EPSサプライヤとして売らないこと:

> 汎用の安全・認証・診断支援としては売らない。既存業務と重なりすぎるためである。

残す場合の最小形:

> 特定案件で、既存資料はあるがOEM向けの短い説明に落とし込めない場合だけ、既存成果物をつなぐ短期支援として扱う。

次にやるなら:

> 1ケースの日本語1枚を作り、それが既存資料の要約を超えるかを見る。超えなければStop。
