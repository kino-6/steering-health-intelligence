# Predictive Value Correction After Internal Fact Error

## 結論

前回の「公開情報とKaggle proxyだけで続ける調査アイテムは全部閉じる」という判断は、強すぎた。
理由は、EPS内部状態やDTC、freeze frame、交換結果が見えないことを、止める主因にしてしまったためである。

このRepoの現行ルールでは、そこにこだわりすぎてはいけない。
Kaggle / 公開proxyを見る目的は、EPS内部の故障事実を当てることではなく、公開proxyだけで「予測のような付加価値」がEPSサプライヤ側に残るかを見ることである。

したがって、修正後の結論はこうである。

Kaggleにあったネタは全滅ではない。
外販商品としてすぐ売れる段階ではないが、公開proxyだけで残せる候補はある。
中心は、車両や用途が「低速・大舵角・凹凸」「荒れた路面と操舵」「通信異常context」のような使用条件classに入りやすいかを先読みまたは分類する方向である。

現時点で残す候補は3つである。

1. 駐車場、低速、大舵角、凹凸が重なる使われ方を先に分類する候補
2. 荒れた路面と操舵入力が重なる使われ方を先に分類する候補
3. 通信異常contextを分類し、操舵系の説明で言ってよいことと言ってはいけないことを分ける候補

これはEPS故障予測ではない。
EPS交換時期予測でもない。
安全保証でも、保証費削減でも、root cause断定でもない。

公開proxyから作る「使用条件の先読み」であり、それがEPSサプライヤの製品企画、診断企画、品質改善、評価企画、顧客技術説明に使えるかを見る候補である。

## 何を修正したか

修正前の判断は、次のように考えていた。

> EPS内部状態、DTC、freeze frame、交換結果が見えないので、Kaggle/public proxy方向は外販商品としてStop。

これは、旧テーマのKillロジックとしては自然だった。
しかし、今回のKaggle / Public Proxy Predictive Value Ruleでは不適切である。

修正後は、次のように見る。

> EPS内部状態が見えなくても、公開proxyだけで使用条件、路面・振動、操舵要求、通信異常contextを先読みまたは分類できるなら、それ自体がEPSサプライヤの業務価値になる可能性がある。

ただし、以下は言わない。

- EPS故障が分かる
- EPS残寿命が分かる
- 交換時期が分かる
- 保証費が下がる
- 安全性が保証できる
- 低速操舵や荒れた路面が故障原因である

## 市場需要

低速取り回し、駐車、狭い場所での大舵角操作、段差、荒れた路面、振動、stop-start、通信異常は、ユーザやサービス現場にとって分かりやすい困りごとになりやすい。

EPSサプライヤにとっても、こうした使われ方を「故障原因」としてではなく、用途別の使用条件classとして整理できれば、製品説明、診断説明、品質改善、評価代表性の会話に使える可能性がある。

ここで重要なのは、EPS内部の故障事実を当てることではない。
公開proxyだけで、どのような使用条件に入りやすいかを先に分類できることが価値になり得る、という点である。

## 未解決の痛み

公開proxyは豊富にあるが、それをEPSサプライヤの業務成果物へ変換する言葉がまだ弱い。

例えば、Kaggleには操舵角、走行挙動、路面状態、交通状態、通信異常のproxyがある。
しかし、それをそのまま出すと、一般的な運転行動分析、路面分類、ADAS制御、汎用IDSに見えやすい。

EPSサプライヤ側の価値にするには、以下へ変換する必要がある。

1. どの用途・車種・走行環境で、EPSの低速取り回し価値を説明しやすいか
2. どの使用条件で、DTC有無にかかわらずサービス説明が難しくなりやすいか
3. どの路面・操舵contextで、品質改善や評価代表性の見直しに使えるか
4. どの通信異常contextで、操舵系の説明に使ってよい情報と使ってはいけない情報を分けるべきか

## ID別の修正判断

| ID | 修正後判断 | 理由 | 次に見ること |
|---|---|---|---|
| `PVC001` | 継続候補。ただし外販商品ではなく、公開proxy価値の本線 | 使用負荷classの先読みは、EPS内部事実なしでも成立する可能性がある | どの部署のどの成果物に転記できるか |
| `ULC008` | 最有力候補 | 駐車場、低速、大舵角、凹凸は、製品企画と診断企画の両方に説明しやすい | 用途別価値説明と診断説明境界の2面で見る |
| `ULC004` | 二番手候補 | 荒れた路面と操舵は、品質改善、評価企画、顧客技術説明に使える可能性がある | 既存NVH/耐久評価の言い換えで終わらないか |
| `PVC004` | 境界候補 | 通信異常contextは、EPS故障予測ではなく、説明の信用境界として使える | 汎用IDSやCSMS/TARAに吸収されないか |
| `KGL003/005/006/007/008` | 中核入力 | 速度、操舵、路面、traffic、凹凸proxyとして使える | EPS内部状態ではなく、使用条件classの入力として扱う |
| `KGL001/002` | 現テーマ外 | 製造・EOL、評価時間予測であり、ユーザーの現在の問いとは別枝 | 別テーマとして明示的に再開する場合だけ見る |
| `KGL004/011` | 境界入力 | 通信異常contextとして使える | EPS故障証拠ではなく、説明境界として使う |

## 正しいKill条件

この方向を止める理由は、EPS内部の事実が見えないことではない。

正しいKill条件は、次である。

1. 使用条件classを作っても、製品企画、診断企画、品質改善、評価企画、顧客技術説明のどの成果物にも転記できない
2. 一般的な運転行動分析、路面分類、ADAS制御、汎用IDSと区別できない
3. 価値を説明するために、故障予測、交換時期予測、保証費削減、安全保証、原因断定へ寄せる必要がある
4. EPSサプライヤが主語になれず、OEM fleet platformやサービス事業者の領域に完全に吸収される
5. 既存の製品説明、診断説明、品質分類、評価代表性確認と同じ言葉にしかならない

## EPSサプライヤとしての言い方

言ってよいこと:

> Kaggleや公開proxyから、低速、大舵角、凹凸、荒れた路面、操舵要求、通信異常contextのような使用条件classを先に分類できる可能性がある。これはEPS故障予測ではなく、EPSサプライヤが製品企画、診断企画、品質改善、評価企画、顧客技術説明で使えるかを見る材料である。

まだ言ってはいけないこと:

> 公開proxyからEPS故障、残寿命、交換時期、保証費削減、安全性、root causeが分かる。

> 駐車操作、低速高操舵、荒れた路面、通信異常がEPS故障原因である。
