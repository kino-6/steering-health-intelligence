# 166. 前駆指標の検証結果 v1(不成立)と、プロトコルv2の事前登録

## 判定

**事前登録([docs/165](165_precursor_protocol.md))の基準に対し、不成立。**

| 基準 | 閾値 | 結果 |
|---|---|---|
| A1 先行性 | 6デバイス中4以上 | **3/6 → FAIL** |
| A2 単調性 | 6デバイス中4以上で ρ≥0.8 | **0/6 → FAIL**(ρ = 0.32〜0.64) |
| A3 温度非依存成分 | 合否判定なし | **評価不能**(後述の欠陥2) |
| B1 ベースライン安定性 | 測定値を報告 | 兆候前の変動幅 **6.8% 〜 14.3%** |

数表: [data/mosfet_precursor.tsv](../data/mosfet_precursor.tsv) / 実行: `python3 scripts/mosfet_precursor.py`

## プロトコルの欠陥2件(実行して初めて分かった)

### 欠陥1: 導通ゲートを書き忘れた

[docs/165](165_precursor_protocol.md) は指標を「steadyStateレコードの median(drainSourceVoltage / drainCurrent)」と定義したが、
**この装置はPWM駆動であり、レコードは二峰性である**。

| 状態 | drainCurrent | drainSourceVoltage |
|---|---|---|
| 導通 | 2.3 〜 2.9 A | 約 4.9 V |
| 非導通 | 0.04 〜 0.07 A | 約 5.58 V(電源電圧がそのまま) |

両者を混ぜて中央値を取ると、**劣化ではなく混合比が値を決める**。実際、修正前の実行では R_on が 1.9 Ω → 83 Ω → 2.4 Ω と乱高下した(30〜40倍)。

**修正**: 各runの導通電流の二峰構造から `(p10+p90)/2` を閾値として導通レコードのみを採る。
**この規則はデータ構造から定義したもので、基準の合否を見て決めていない。** 修正後の R_on は 1.7 〜 2.3 Ω に収まり、物理的に妥当になった。

### 欠陥2: 温度整合の窓が使えなかった

A3 は「run 1 の median packageTemperature ±2°C」で温度を揃える設計だった。しかし
**パッケージ温度は実験計画上、run とともに系統的に約20°C下がる**(152°C → 133°C)。

そのため run 2 以降で窓に入るレコードが**1件も無く**、A3は空振りした。**評価不能である。**

## 不成立の原因は見えている(ただし後付けの説明である)

導通ゲート修正後の値を並べると、構造がはっきりする。Test_14 の例:

| run | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|
| T_pkg [°C] | 152.6 | 147.7 | 142.4 | 137.7 | 135.0 | 134.6 | 133.9 |
| R_on [Ω] | 1.873 | 1.815 | 1.781 | 1.754 | **2.070** | **2.192** | **2.265** |

**run 1〜4 では R_on は温度に追随して下がり、run 5 以降は温度がほぼ平らなのに R_on だけが上がる。**
6デバイスすべてで同じ形が出ている。

つまり **R_on は温度に支配されており、劣化成分はその上に乗っている**。
事前登録した指標(生のR_on)は温度を制御していないため、単調性(A2)は原理的に成立しえなかった。
A3がそれを担うはずだったが、窓の設計を誤って空振りした。

**この説明は後付けである。** v1の判定は不成立のままとし、指標を差し替えて再判定しない([docs/161](161_pmsm_model_validation_protocol.md) と同じ扱い)。

## B1 の測定値(これは v1 でも意味がある)

兆候発生前の run における R_on の変動幅:

| デバイス | Test_8 | Test_9 | Test_10 | Test_11 | Test_12 | Test_14 |
|---|---|---|---|---|---|---|
| 変動幅 | 7.7% | 14.3% | 13.8% | 11.1% | 10.7% | 6.8% |

**同一個体の基準は、兆候が出る前に 7〜14% 動く。** ただしこの変動の大半は上記のとおり温度由来であり、
**温度を制御すればもっと小さくなるはず**である。v2で分離する。

# プロトコル v2(実行前に固定)

**以下は v2 の結果を見る前にコミットする。**

## 変更点(2つだけ)

1. **導通ゲート**を指標の定義に含める(欠陥1の修正)。閾値は各runの `(p10+p90)/2`
2. **温度整合を、固定窓から回帰残差へ変える**(欠陥2の修正)

## v2 の指標

各デバイスについて、**自分の初期runだけを使って** R_on と T_pkg の線形関係を推定し、以後のrunをその関係からの残差で見る。

```
初期run(run 1〜3)で        R_on = a * T_pkg + b   を最小二乗で推定
各runについて              residual = median(R_on) - (a * median(T_pkg) + b)
指標                       Δ = residual / (a * median(T_pkg_run1) + b)     [ベースライン比]
```

- **初期runを1〜3に固定する。** run 4以降は劣化が入りうるため回帰に使わない。この境界は結果を見る前に決めた
- 温度係数 a はデバイスごとに推定する(個体基準、[docs/163](163_per_unit_baselining.md))

## v2 の判定基準(実行前に固定)

| # | 基準 | 閾値 |
|---|---|---|
| **A1'** | 最終run(7)より前に Δ が **+5%** を超える run が存在する | **6デバイス中4以上** |
| **A2'** | run 4〜7 における run順 vs Δ の Spearman ρ | **6デバイス中4以上で ρ ≥ 0.8** |
| **B1'** | 回帰に使った run 1〜3 における残差の変動幅 | 測定値を報告(温度を除いた個体基準の安定性) |

**禁止**: 初期runの範囲(1〜3)を結果を見てから変えない。閾値+5%を変えない。デバイスを除外しない。
不成立ならそのまま記録する。**v3は作らない**——2回目の指標変更で止める。

## v2 で成立した場合に言えること

> 温度の影響を個体ごとに除いたうえで、**部品内部の電気量には hard failure に先行する情報が乗る**。
> 先行の幅は run 単位で N 段階分である。

## v2 でも不成立の場合に言えること

> 実部品の連続追跡でも、温度を除いた先行兆候は確認できなかった。

## Rule Check

- v1の不成立を、原因が分かった後も**判定として維持**した
- 欠陥2件を、指標を有利に変える口実にせず**プロトコルの誤りとして記録**した
- v2を実行前にコミットし、初期runの範囲・閾値・禁止事項を先に固定した
- **v3を作らないことを先に宣言した**(基準を通るまで叩かないため)
