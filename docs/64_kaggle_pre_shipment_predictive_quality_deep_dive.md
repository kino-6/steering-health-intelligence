# Kaggleから出荷前の予知保全を深掘りする

## 結論

ここで言う「予知保全」は、出荷後の車両が将来壊れるかを見る話ではない。
EPSサプライヤの製造、検査、評価の途中で、後で不合格、再検査、保留、手戻りになりそうな個体や条件を先に見つける話である。

自然な言い方をすると、これは **出荷前の品質予兆検知** である。

Kaggleから得られる一番重要な情報は、以下である。

> Boschの課題は、製造ラインの各工程で記録された大量の測定・試験データから、最終的に品質管理で落ちる部品を予測するものだった。これは、EPSサプライヤが持てる工程データ、EOL検査データ、再検査結果にかなり近い。

したがって、次に進めるなら、狙いは次の1つに絞る。

> EPS製造・EOL検査のデータを使い、後工程で不合格、再検査、保留になりそうな個体を早く見つけ、再検査、保留、工程確認の優先順位を出す。

Mercedes-Benzのテスト時間予測も有用だが、こちらは2番手である。
理由は、評価時間短縮の需要はありそうだが、EPSの評価時間がvariantやsoftware/calibrationでどれだけ変わるかは公開情報だけでは分からないためである。

## 用語の整理

誤解しやすいので、ここを分ける。

| 言い方 | 何を見るか | 今回の扱い |
|---|---|---|
| 出荷後の予知保全 | 市場に出た車両や部品が将来壊れるか | 今回は扱わない |
| 車両runtime監視 | 車両搭載中のEPS状態や異常を走行中に見る | OEM/fleet依存が強いので主対象外 |
| 出荷前の品質予兆検知 | 製造・検査・評価中に、後で落ちそうな個体や条件を先に見る | 今回の本命 |
| 評価時間の予測 | 構成や試験条件からbench/HILS/EOL時間を見積もる | 2番手 |

## Kaggleから得られた具体情報

### Bosch Production Line Performance

公開情報から分かること:

- 製造ライン上の部品ごとに、測定値、カテゴリ値、測定時刻が大量に記録されている
- 特徴量名は、ライン、ステーション、測定項目を示す形になっている
- 目的変数は、品質管理で落ちるかどうかの二値判定である
- 不合格はかなり少ない希少事象である
- データは匿名化されており、外部参加者は工程の物理的意味を知らない
- それでも、ライン、ステーション、時刻、部品の流れ、同じ測定値の繰り返し、短期/長期の不良率変化が予測に効いていた

EPSサプライヤへの読み替え:

| Kaggle上の要素 | EPS製造・検査への読み替え |
|---|---|
| 部品ID | EPS ECU、motor、sensor、assembly、rack/module等の個体ID |
| Line / Station | 実装、組付、calibration、電気検査、機能検査、音響検査、EOL検査 |
| Numeric feature | 電流、電圧、トルク、角度、温度、抵抗、応答時間、振動、音、通信応答などの測定値 |
| Categorical feature | variant、ライン、治具、設備、software/calibration、検査レシピ |
| Date feature | 工程通過時刻、設備稼働タイミング、ロット、直前/直後個体の関係 |
| Response | EOL fail、retest、hold、scrap、工程戻し、特採、再調整 |

重要なのは、Kaggleの勝ち筋そのものではない。
EPSで使うなら、次の3点が価値になる。

1. 個体単位で、後工程の不合格や再検査を先に拾う
2. 工程・ステーション単位で、怪しい測定グループを見つける
3. 時刻や順序から、設備・ロット・直前個体の影響を疑う

### Mercedes-Benz Greener Manufacturing

公開情報から分かること:

- 車両構成を匿名化した特徴量から、テストベンチにかかる時間を予測する課題である
- 入力はカテゴリ特徴と多数の二値特徴で構成される
- 目的変数はテスト時間である
- 構成によってテスト時間が変わるため、評価計画や待ち時間削減に接続できる

EPSサプライヤへの読み替え:

| Kaggle上の要素 | EPS評価への読み替え |
|---|---|
| Vehicle configuration | EPS variant、software、calibration、motor type、sensor type、diagnostic option |
| Binary feature | 機能有無、診断有無、制御モード、評価項目の有無 |
| Test bench time | HILS、bench、EOL、release評価の実行時間 |
| Long-tail time | 特定variantや評価組み合わせで時間が伸びる条件 |

こちらの価値は、品質予兆というより、評価運用の予測である。
EPSで意味が出るのは、次のような場合である。

- variantやsoftware/calibrationで評価時間が大きく変わる
- 試験待ちや設備占有が開発日程の痛みになっている
- 評価時間の見積もりが経験依存で、計画時に外れやすい

## 市場需要

市場需要は、エンドユーザの故障通知ではない。
EPSサプライヤ内部の製造品質と評価運用の需要である。

製造側の需要:

- 後工程で不良が見つかる前に、怪しい個体を先に見たい
- EOL failやretestを、工程中のデータから早めに予兆として拾いたい
- 不良率が低いからこそ、全件を同じ目で見るのではなく、怪しい個体を優先したい
- 工程、設備、ロット、時刻、直前個体の影響を疑える材料が欲しい

評価側の需要:

- variantやsoftware/calibrationが増えて、試験時間が読みにくい
- bench/HILS/EOL設備の占有時間を見積もりたい
- 時間がかかる構成を先に見たい
- 評価計画を、経験だけではなく過去データで補強したい

## 仮説

### 最有力仮説: 出荷前品質スクリーニング

EPSサプライヤは、製造ライン、工程検査、EOL検査の測定データを使って、後で不合格、再検査、保留になりそうな個体を早く見つけられる可能性がある。

出力は、故障予測ではない。
出力は、次のような現場判断である。

- この個体はEOL前に追加確認する
- この個体はEOL後に再検査へ回す
- この個体群は同じ工程・設備・時刻に偏っているので工程確認する
- この測定グループは品質判定に効いていそうなので管理項目候補にする

### 2番手仮説: 評価時間スクリーニング

EPSサプライヤは、variant、software、calibration、試験項目、診断設定から、bench/HILS/EOL評価時間を見積もれる可能性がある。

出力は、評価短縮の断定ではない。
出力は、次のような評価計画支援である。

- この構成は時間がかかりそうなので先に枠を押さえる
- この試験セットは設備占有が長い
- このvariantは過去にretestや長時間化が多い
- release gate前に時間リスクを見積もる

## 解決策

初期提供物は、次の3つに絞る。

1. 出荷前品質スクリーニングのデモ
2. 評価時間スクリーニングの小さなデモ
3. 現場判断へ貼る1枚

最初に作るべきは1である。

デモで見るべき指標は、単なる正解率ではない。
不良が少ないので、正解率は役に立ちにくい。
見るべきは、次である。

- 上位1%、5%、10%の要注意個体に、fail/retest/holdがどれだけ含まれるか
- 見逃しと過検出のバランスが現場判断として許容できるか
- どのライン、ステーション、測定グループ、時刻帯が効いているように見えるか
- その説明が工程確認や再検査判断に使えるか

## Kaggleからの学び

### 1. 希少な不良を扱う必要がある

Bosch型では、不良がかなり少ない。
これはEPSでも自然である。
量産品質では、不良は多数派ではない。

したがって、通常の正解率ではなく、要注意個体の上位リスト、再検査優先順位、見逃し率、過検出率を見るべきである。

### 2. 工程順序と時刻が重要になる

Bosch型では、ライン、ステーション、部品の通過順序、時刻の情報が重要になる。
EPSでも、単独の測定値だけでなく、工程順序、設備、ロット、直前/直後個体、時刻帯を見るべきである。

これは、単なる表形式MLより、工程文脈の特徴量設計が価値になることを示す。

### 3. 匿名化データはデモには使えるが、現場改善には限界がある

Kaggleでは特徴量が匿名化されている。
そのため、モデル精度を出せても、「この物理量を直せ」とは言いにくい。

EPSサプライヤで価値にするには、実データでは匿名化しない形で、工程名、測定名、検査項目、設備、レシピ、software/calibrationを残す必要がある。

### 4. 既存工程管理と被る

工程管理、統計的工程管理、品質管理、MES、BIは既に存在する。
したがって、価値があるのは「工程を監視する」ではなく、個体単位で次のアクションを出す場合である。

具体的には、再検査、保留、工程確認、追加測定、評価時間見積もりである。

## EPSサプライヤ向けの成果物案

| 成果物 | 何をするか | 誰が使うか | 価値が出る条件 |
|---|---|---|---|
| 要注意個体リスト | 後でfail/retest/holdになりそうな個体を順位付けする | EOL検査、製造品質 | 上位リストで実際のfail/retest候補を拾える |
| 工程グループ説明 | どのライン、ステーション、測定グループ、時刻帯が効いていそうかを示す | 工程設計、品質保証 | 工程確認や設備確認に転記できる |
| 再検査判断メモ | なぜ再検査/保留/工程確認するかを1枚にする | EOL検査、品質保証 | 現場が判断理由を説明できる |
| 評価時間見積もり表 | variantやsoftware/calibration別に評価時間を見積もる | 評価計画、HILS/bench | 計画時の待ち時間や設備占有が痛みになっている |
| 禁止主張リスト | 言ってはいけないことを明示する | 企画、営業、品質 | 故障予測やEOL省略に飛躍しない |

## Business Model

現時点で外販SaaSにはしない。
最初は、固定スコープの検証支援が自然である。

### 初期offer

名前をつけるなら、まだ仮名でよい。

> 出荷前品質スクリーニング検証

内容:

- 既存の工程・検査・EOLデータ項目を棚卸しする
- fail/retest/hold/scrapなど、現場判断に直結するラベルを決める
- 上位リスク個体を抽出する
- 工程グループ説明を作る
- 再検査/保留/工程確認に貼る1枚を作る

買い手:

- 製造品質
- 工場品質保証
- EOL検査
- 工程設計

2番手offer:

> 評価時間スクリーニング検証

内容:

- variant、software、calibration、試験セット、設備、実行時間を棚卸しする
- 評価時間が伸びる構成を見積もる
- 試験計画や設備占有のリスクを1枚にする

買い手:

- 評価計画
- HILS/bench評価
- software/calibration release gate担当

## 検証方法

内部資料を使わない現行方針では、まずKaggleで型を作る。

Bosch型デモで見ること:

- ライン、ステーション、測定種別、時刻から特徴量を作れるか
- rare failを上位リスク個体に集められるか
- 上位リスク個体を見た時、再検査/保留/工程確認という現場アクションに翻訳できるか
- 匿名化により説明が限界になることを明示できるか

Mercedes型デモで見ること:

- 構成特徴から評価時間をどの程度読めるか
- 長時間化する構成を上位リスト化できるか
- 評価計画や設備占有の判断へ翻訳できるか

## Kill条件

次なら止める。

- 上位リスク個体が実際のfail/retest/holdを拾えない
- 拾えても、現場アクションが「様子見」しかない
- 工程名、測定名、設備、時刻、ロットが使えず、工程確認に落ちない
- 既存SPC、MES、BI、品質管理で既に同じ判断ができる
- 評価時間のばらつきが小さく、見積もる価値がない
- EOL省略、保証費削減、出荷後故障予測に話が飛ぶ

## 最終判断

この方向は、今までの探索の中では比較的筋が良い。
理由は、EPSサプライヤが持てないOEM保証DBやfleet dataではなく、サプライヤが持てる製造・検査・評価データに寄せられるためである。

ただし、商品化の主張はまだ早い。
まずはBosch型の公開データで、以下を示すべきである。

> 上位リスク個体を抽出し、工程グループ説明を付け、再検査/保留/工程確認に貼る1枚を作れるか。

これができなければ、Kaggle方向もただのMLデモで止める。
