# 報告の型

**このRepoでユーザに結果を報告するときは、必ずこの型に従う。**
2026-08-26、「使えない新人と会話しているようだ」という指摘を受けて作った。
下の「よくやる失敗」はすべて実際にやった失敗である。

## 大原則3つ

### 1. 結論を先に置く(BLUF / Minto Pyramid)

**最初の3行で「何が変わったか」を書く。** 手順・スクリプト名・記号・経緯を先頭に置かない。
読み手は最初の3行を読んで、続きを読むかどうかを決める。

> Minto Pyramid Principle: 答えを先に出し、その後に根拠をグループ化し、最後にデータを置く。
> — [betterup](https://www.betterup.com/blog/minto-pyramid) / [Think Insights](https://thinkinsights.net/strategy/pyramid-principle)

- ○ 「熱経路は劣化していませんでした。だから心配していた誤差要因は小さい側です」
- × 「docs/198の事前登録を無修正で実行しました。T1は0/6で…」

### 2. 作業ではなく変化を書く(outcome, not activity)

**やったことの一覧は報告ではない。** 何が分かって、何が変わったかを書く。

> 活動報告(マージしたPRの一覧)ではなく成果(デプロイ失敗が30%減った)を書く。
> — [MergeScout](https://mergescout.com/blog/how-to-write-engineering-team-report/)

- ○ 「オン抵抗だと思って測っていた量が、実は別物でした」
- × 「transientとpwmTempControllerStateを開きました」

### 3. 不成立は「誰の何が外れたか」を書く

**「不成立」「FAIL」だけを書くと、データが悪いと読まれる。** データは正しい。
外れたのは**こちらの予想**である。予想の主語を必ず書く。

> 「実験は失敗した」ではなく「予想した結果は出なかった。これは対象条件下でその変数が効かないことを示す」と書く。
> 非有意な結果は「AとBは同じ」を意味しない。
> — [ServiceScape](https://www.servicescape.com/blog/how-to-write-about-negative-or-null-results-in-academic-research) / [Beyond the null (Cell iScience)](https://www.sciencedirect.com/science/article/pii/S2589004224029031)

- ○ 「**私は熱経路が劣化すると予想しましたが、6個体とも劣化していませんでした**」
- × 「T1は0/6で不成立でした」
- × 「熱経路は劣化していないことが証明されました」(非有意は同一性の証明ではない)

## 毎回入れる4行

報告の冒頭に、この4つを必ず書く。

1. **使ったデータ**: 名前と、**新規取得か既存か**。(「NASA公開のMOSFET、前回と同じ6個体」)
2. **わかったこと**: 1〜2文。記号なし。
3. **それで何が変わったか**: 主張が強くなった/弱くなった/変わらない。
4. **訂正があれば最初に**: 過去の記述を取り下げる場合、他の何より先に書く。

## よくやる失敗(全部やった)

| 失敗 | 直し方 |
|---|---|
| `P1` `T1` `ρ` `R2` などの記号を本文に出す | **日本語で書く。**記号は数表とdocsの中だけ |
| 事前登録の判定表を冒頭に置く | 判定は根拠。**結論の後ろ** |
| 手順・スクリプト名・コミットを先に書く | 末尾に1行 |
| 表を並べて結論を書かない | **表の前に、その表が何を言っているかを1文** |
| 「不成立」とだけ書く | **誰の何が外れたかを書く** |
| 長い | 結論部分は**10行以内**。根拠は畳む |
| 締めが「誰かに見せる/売る/反応を得る」 | **禁止。**[AGENTS.md](../../../AGENTS.md) ルール0。手を動かして埋まるものを次に置く |
| 自分の誤りを後半に隠す | **先頭に出す** |

## テンプレート(この5節ちょうど。増やさない・減らさない)

**2026-09-01、「報告が意味不明」と再度指摘された。**
この Skill は既に存在していたのに守れなかったので、**型を機械で検査する形にした。**

```
## 答え
<問いへの答え。3文以内。前回と同じなら「変わっていません」と書く>

## 前回からの変化
<何が動いたか。動いていないなら、動いていないと書く>

## 根拠
<数字。この Repo の外で意味が通る単位で。「床の◯倍」には必ず実寸を添える>

## この答えが崩れる条件
<1〜2文>

## 作業
<スクリプト・検査・コミット・文書番号は、全部ここに1〜2行で>
```

**送信前に必ず通す:**

```sh
python3 scripts/check_report.py <下書き.md>
```

**止めるもの**: 5節の欠落／「答え」が3文超／内部記号(事前登録の記号・シート番号)／
ファイル名・道具の名前が「作業」節より前にあること／自分の作業の話が前に出ていること／
実寸の無い「床の◯倍」／全体1,400文字超。

## 診断 — なぜ意味不明になっていたか

**私の報告は「私の作業に何が起きたか」を書いていて、「問いの答えが今どうなっているか」を書いていなかった。**

直近の報告を機械にかけると、本文に**自分の作業の話が6箇所**、道具の名前が3箇所あり、
**問いへの答えは1行も無かった。**読者は文書番号を全部追っていないと何も取り出せない。

**したがって「答え」を最初の節として強制し、作業を最後の節に押し込んだ。**

## 報告してよいタイミング

**[loop](../loop/SKILL.md) を先に見る。**
`QUESTION.md` に開いている項目が残っている間は、**検証が1本終わっても報告しない。**
報告の単位は**問いの粒度**であって、自分の作業の粒度ではない。

## 送信前にもう1つ

**[troubles](../troubles/SKILL.md) を回す。**過去に虚偽・思い込みで不成立になった22の型を当てる。

## 自己チェック(送信前)

- [ ] 最初の3行に記号・スクリプト名・手順が入っていないか
- [ ] 「不成立」を書いたなら、**予想したのは誰か**が書いてあるか
- [ ] 使ったデータが新規か既存か書いたか
- [ ] 表の前に、その表の意味が1文で書いてあるか
- [ ] 訂正が先頭にあるか
- [ ] 締めが外部依存(見せる・売る・反応)になっていないか
- [ ] 結論部分が10行を超えていないか
- [ ] **[troubles](../troubles/SKILL.md) の22の型を当てたか**
