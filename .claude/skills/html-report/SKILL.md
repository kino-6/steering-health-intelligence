# HTML レポートの型

**HTML を手で書かない。JSON を埋めて、`report_render.py` に描かせる。**

2026-09-10 に作った。それまでの HTML レポートは全部手書きで、次の 3 つが起きていた。

1. **SVG の座標を手で打っていた。**軸と数字が食い違っても、誰も気づかない
2. **同じ指摘を何度も受けた。**平易な日本語・折り畳み・グラフ・成立を先に。文章で決めただけなので守れない
3. **文章が増えて、データが減った。**「ポエムのようなので見る価値を感じない」と言われた

**直し方は AGENTS.md と同じである。機械で検査できないかを先に考える。**

## 3 段

```sh
# 1. JSON を埋める            <- ここだけが人(LLM)の仕事
vi reports/<name>.json

# 2. 検査に通す               <- 通らなければ描かない
python3 scripts/check_report_json.py reports/<name>.json

# 3. 描く                     <- SVG も含めて全部スクリプトが作る
python3 scripts/report_render.py reports/<name>.json -o <out>.html

# 4. 描いた後をもう一度検査     <- 潰れ・重なり・色・字の大きさ
python3 scripts/check_report_style.py <out>.html
```

**検査は 2 回ある。**JSON の検査は書いた内容を見る。**描画後の検査は、描かれた絵を見る。**
文字が箱からはみ出しているか、2 つのラベルが重なっているか、
暗いモードで読めない色になっているかは、**描くまで分からない。**

**通ってから Artifact に publish する。**publish は既存の URL に上書きする(`url` を渡す)。
`<out>.html` は body の中身だけで、`<!doctype>` や `<head>` は書かない。Artifact 側が包む。

## JSON の形

```jsonc
{
  "title":   "…",                  // 短い名前。説明を足さない
  "eyebrow": "…",                  // 上に出る小さい英字ラベル
  "lede":    "…",                  // 1〜2文
  "terms":   ["T1","R_on"],        // 記号に見えるが、この分野の名前であるもの
  "answer": {
    "holds": ["成立していること", …],   // 空にできない。成立を先に置く
    "fails": ["成立していないこと", …]  // 空にできない
  },
  "sections": [ { "role":"検証", "h":"見出し", "en":"english", "blocks":[ … ] } ],
  "scope":   [ {"k":"データ","v":"…"}, … ],
  "sources": ["…"]
}
```

### 章立ては、確立された様式から借りる

2026-09-13「世の中のフォーマットを調査して学んでほしい。それで再構築して」。
調査と根拠は [docs/359](../../../docs/359_report_format_survey.md)。**自分で章立てを考えない。**

| role | 章 | 中身 | 借りた様式 |
|---|---|---|---|
| `要旨` | 要旨 | 6 段: 分野 → 背景 → 問題 → 主結果 → 従来との違い → 意味。**数字は最小限** | Nature summary paragraph |
| `序論` | 1 | 背景と問題、目的と範囲、章立て | IMRaD |
| `用語` | 2 | この文書での語の意味。造語は使わない | ISO の 3 章 |
| `方法` | 3 | しくみ、データ構造、計算、使ったデータ、仮想の接続、検証の進め方 | IMRaD |
| `結果` | 4 | 検証を 4.1, 4.2 … と並べる。**見出しに番号を書かない**（描画側が振る） | IMRaD |
| `考察` | 5 | 成立したこと、**計画からの逸脱**、**残るリスク**、限界 | ISO/IEC/IEEE 29119-3 §7.4.3, 7.4.7 |
| `結論` | 6 | 成立／不成立の 2 列（`answer`）、位置づけ | IMRaD |
| `参考文献` | — | `references` を番号付きで描く | 全様式 |
| `付録` | A, B … | 全パラメータ、改訂の記録 | 29119-3 §5.2.4 |

冒頭の `front` に 29119-3 §5.2 の共通情報を書く: 識別、発行、状態、改訂。
要旨・用語・結論・参考文献は 1 個ずつ。序論・方法・結果・考察・付録は小節（1.1, 1.2 …）を持てる。検査が順番を見る。

### ブロックの種類

| type | 中身 | 備考 |
|---|---|---|
| `p` / `lead` / `small` / `note` | 文章。`text` に HTML 断片を書いてよい | `note` は訂正・取り下げ用。左に赤い線が付く |
| `h3` | 節の中の小見出し | |
| `table` | `cols` / `rows` / `fold` / `note` / `stripe` | `cols` の要素を `{"t":"名","n":true}` にすると右寄せの数値列 |
| `chart` | `kind` + データ + `source` + `alt` + `caption` | 下記 |
| `bytes` | `total` + `fields:[{"name","t"\|"bits","key","why"}]` | 下記 |
| `eq` | 式。`<b>` で強調 | |
| `kpi` | `items:[{"k":"…","v":"…","tone":"y|n"}]` | 見出し行の数字帯 |
| `fold` | `summary` + `blocks` | 中に何でも入れられる |
| `sequence` | `actors` / `steps` / `phases` + `source` + `alt` + `caption` | 下記 |
| `svg` | `viewBox` / `body` / `alt` / `caption` | **逃げ道。**流れ図など、データではない絵だけに使う |
| `key` | `items:[…]` | 節の先頭の要点。3〜5 行 |
| `ul` | `items:[…]` | 箇条書き |

### `bytes` — データ構造は、幅で描く

```jsonc
{"type":"bytes", "total":30,               // バイト数。合わないと描かせない
 "fields":[{"name":"deviation","t":"f32","key":1,"why":"…"},
           {"name":"flags","t":"u8","why":"…"}],
 "alt":"…", "caption":"…", "fold":"…"}
```

**箱の幅は型から計算する。**`f32` は `u8` の 4 倍の幅になる。
ビット単位のものは `t` の代わりに `"bits": 3` を書く。目盛りがビット位置に切り替わる。
**同じ `fields` から、位置・大きさ・意味の表も自動で作る。**図と表が食い違えない。

2026-09-10、「データ構造、このレポート形式でどうしてOKになるのかわからない」と言われた。
**OK ではなかった。**それまでは全フィールドが同じ幅の箱で並んでいて、
4 バイトの浮動小数点と 1 バイトのフラグが同じ大きさに見えていた。**レイアウトが読めない。**

### `sequence` — 動的構造を書く

```jsonc
{"type":"sequence", "source":"derived",
 "actors":[{"id":"ecu","name":"走行中の ECU"}, …],
 "phases":[{"label":"走行中ずっと","from":2,"to":5}],   // steps の添字
 "steps":[{"from":"ecu","to":"bus","text":"2 バイト","when":"100 ミリ秒ごと"},
          {"self":"ecu","text":"標本を取る","when":"10 Hz"}],
 "alt":"…", "caption":"…"}
```

2026-09-11「経路はあるがシーケンスはない。動的構造を記述してはどうか」。

**経路の図（`svg`）と、この図は別の仕事をする。**経路はどの箱がつながっているかを言う。
**シーケンスは、1 回だけ起きることと、100 ミリ秒ごとに起きることと、
事象のときだけ起きることを分ける。**`when` に条件と周期を書く。
**`phases` で「出荷時」「走行中」「入庫時」を帯にする。**

### グラフ 4 種

**座標は一切書かない。値だけ渡す。**目盛りは値から計算されるので、
軸に出た数字は必ずグラフが届く値になる。

| kind | 使いどころ | 必要なもの |
|---|---|---|
| `barh` | 項目ごとの大きさを比べる | `series:[{label,value,color}]`, `unit`, `axis` |
| `barv` | 順番のある量。棒の中に注記を入れられる | `series:[{label,value,note}]`, `ylabel`, `axis` |
| `line` | 何かを振ったときの動き。複数系列 | `x:{values|labels,title,unit}`, `series:[{name,values,endlabel}]` |
| `dots` | 生の点を全部打つ。平均を取らない | `rows:[{label,values,point_labels}]`, `axis` |

`line` には 3 つの重ねものを足せる。`hlines` は自分で置いた線などの横線、
`marks` は実測値の位置などの縦線、`events` はデータの上に赤い丸を置く（警報が出た点など）。

**縦軸は 0 から始まらない。**データが入る範囲に合わせて自動で決まる。
**データが軸の 35% を埋めていなければ、描かずに止まる。**
件数や割合のように 0 が意味を持つときだけ `"zero": true` を書く。棒グラフは常に 0 から。

2026-09-11「知りたいのは 0.8 から 1.0 くらいの範囲であり、そこをフォーカスすべき。それは検出できないの?」
検出できる。0 から 1.5 の軸に 0.82 から 1.02 のデータを描いていた。

**`source` は必須。**`measured` / `simulated` / `assumed` / `derived` のどれか。
図の説明の左肩に「実測」「仮想」「置いた値」「計算」と出る。
**「仮定した格子は根拠ではない」を、図の側で強制する仕掛けである。**

## 検査が止めるもの

| | 何を止めるか | いつ言われたか |
|---|---|---|
| **R0** | 「自社」「当社」「弊社」「社内」「顧客」など | 2026-09-07「社内用語はありません。これは個人研究です」 |
| **R1** | この研究だけの造語（「指紋」「床」「判定を出す」、記録器の意味の「要素」） | 2026-09-08「指紋って一般的？」、2026-09-13「一般的な日本語ではなく混乱を生じさせる」 |
| **R2** | `holds` か `fails` が空 | 2026-09-09「劣化具合出せてないじゃん」 |
| **R3** | 「——」・1文 90 文字超・体言止め（警告） | 2026-09-07「レポートの記述が気持ち悪すぎる」 |
| **R4** | 文章の中の改行 | 2026-09-08「無駄に横幅が制限されており不要な改行が生成されている」 |
| **R5** | 表・図・式の直前に説明の1文が無い | report Skill「表の前に、その表が何を言っているかを1文」 |
| **R6** | 図に `alt` か `caption` が無い | |
| **R7** | 8 行を超える表が畳まれていない | 2026-09-08「レポートは折り畳みをしっかり使って」 |
| **R8** | 文章が全体の 55% を超える | 2026-09-08「ポエムのようなので見る価値を感じない」 |
| **R9** | 本文の数字が、表にも図にも無い（警告） | 2026-09-08「数字だけ出されてもグラフでわかりやすくして」 |
| **R10** | 事前登録の記号・ファイル名・道具の名前 | report Skill と同じ |
| **R11** | 図に `source` が無い | 「仮定した格子は根拠ではない」 |
| **R12** | 節の `role` が無い、並びが型どおりでない | 2026-09-11「章立てがよくない」 |
| **R13** | 要点が無い／先頭でない、図表が無い、結果の節に折りたたみが無い、参考文献に url が無い | 2026-09-13「箇条書き・リンク・折りたたみ・図表」 |
| **軸が広すぎる** | データが縦軸の 35% も埋めていない | 2026-09-11「そこをフォーカスすべき」 |
| **はみ出し** | 描いた座標が viewBox の外に出た | 描画時に `report_render.py` が止める |

### 描画後の検査 — `check_report_style.py`

| | 何を止めるか | いつ言われたか |
|---|---|---|
| **字が潰れている** | ラベルが箱の幅より広い。文字幅を推定して比べる | 2026-09-11「字が潰れている」 |
| **字が重なっている** | 2 つの文字の矩形が交わっている | 同上 |
| **字が小さい** | 11.5 px 未満が 1 つでもある。CSS も SVG も見る | 2026-09-11「文字サイズもGateを設けて」 |
| **コントラスト不足** | 明暗どちらのモードでも WCAG AA を下回る組がある | 2026-09-11「Darkmodeなど、Modeに即した色使いにGate」 |
| **未宣言の文字色** | `CONTRAST_PAIRS` に無い色で文字を描いた | 同上。新しい組み合わせを黙って増やせない |
| **数字と単位が離れている** | `30 バイト` の間で折れうる | 2026-09-13「文章の接続を無視した改行」 |

**色は推定しない。**使う色の組は `report_render.CONTRAST_PAIRS` に全部書いてあり、
**明暗の両方で計算する。**出力に現れた文字色がその表に無ければ、そこで止まる。

**灰色と小さい字は、それだけでノイズになる。**
`--ink3` は軸の名前と脚注にしか使わない。本文と図の説明は `--ink2` 以上にする。

**R3 と R9 は警告で、止めない。**止めると、正しい例外まで消して数字を減らす方向に働く。
**残った警告は、残す理由を言えるようにしておく。**

`raw: true` を文章ブロックに付けると R3 と R9 を外れる。**バイト列の引用など、
文章ではないものだけに使う。**言い訳には使わない。

## 節の形は「要点 → 図表 → 畳んだ詳細」

2026-09-13「箇条書きをうまく使って欲しい、何を参考にしたのかリンクを示せてない、
折りたたみをうまく利用して欲しい、図表を利用して欲しい。まだ大学生の方がいいレポート書く」。

| 位置 | ブロック | 規則 |
|---|---|---|
| 節の先頭 | `key` | 3〜5 行の箇条書き。**この節で何が立ったか**を、数字を添えて書く。序論・方法・結果・考察・結論は必須 |
| 次 | `chart` / `table` / `bytes` / `sequence` | 主図 1 枚と表 1 つまでを開いたまま置く。方法・結果・考察は図か表が必須 |
| その後 | `fold` | 小見出し（h3）ごとに畳む。畳む見出しは h3 の文をそのまま使う。結果の節は折りたたみ必須 |
| 本文中 | `[n]` | 参考文献 n へのリンクになる。**出所のある数字には番号を付ける** |
| 末尾 | `references` | `{text, url, note}`。**url が無い項目は通らない**（有償や登録配布なら note に書く） |

`ul` は要点以外の箇条書き。段落 3 つを並べるより、項目が 3 つあるなら `ul` にする。

## 図には、必ず一緒に書くもの

**量を出したら、その量をどう決めたかを同じ節に書く。**
2026-09-11「アシスト能力はどうやって規定したのか、が未記載」。

- **定義**: 何と何の比か。どの式か。**測った量か、計算した量か**
- **前提**: その式が立つ条件。**当てはまらない条件も書く**
- **閾値**: どこで鳴るのか。**閾値が別の量に置いてあるなら、そう書く。**
  この研究では閾値は逸脱に置いてあり、能力に直すと個体ごとに 0.887 から 0.980 までばらつく

## 改行は、文節でだけ折り、両端を揃える。そして出す前に見る

経緯（3 回指摘された）:
1. どこでも折る → 「2 / バイト」「学習し / た」で折れた（2026-09-13 朝）
2. 文節でだけ折り、左揃え → 右端が波打って「悪化してますね」
3. どこでも折るに戻す → 「ユニッ / トが」で折れて「間抜け。改行を何度も指摘させないで」

**根本の原因は、私がページを一度も見ていなかったこと。**改行はブラウザが決めるので、
幅や重なりの検査には映らない。

今の設定（`report_render.py`）:
- budoux で文節に切って `<wbr>` を入れ、`word-break: keep-all` でそれ以外の場所では折らない
- **`text-align: justify` + `text-justify: inter-character`** で右端を揃える。
  長い文節が入らない行は字間が広がる。それが代償で、それ以上は触らない
- 数字と単位は `<span class="nb">` で接着する

**publish の前に必ず描画して見る**（`artifact-design` の「一度見る」を、この Skill では省略しない）:

```sh
# body を暗いテーマの骨組みで包み、Chrome で撮る
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new --disable-gpu \
  --hide-scrollbars --window-size=1300,1500 --screenshot=shot.png "file://.../preview.html"
```

見るのは冒頭 1 画面でよい。**折れ方と字間を自分の目で確かめてから publish する。**

## 初手の画面は文章にする

2026-09-13「目の滑る日本語。正直もう初手から見る気なくなる」。
答えの欄が「〜できます。」「〜です。」の短文の羅列で、**文と文のつながりが無かった。**
1 回目の T39（凝った文体）の反動で、飾りと一緒に接続まで削っていた。

- **`answer.summary` に、数字を減らした要約の段落を書く。**読み手が最初に読むのはここである
- **`holds` / `fails` の各項目は 2 文でつなぐ。**前の文を受けて次の文を書く
- **1 文ごとに独立した事実を並べるなら、それは表にする。**文章にするなら、つなぐ
- 数字は数字帯（`kpi`）と表に置く。答えの文章に入れるのは、その文が成り立つのに要る数字だけ

## 埋めるときの順番

1. **`answer` から書く。**成立を先に、不成立を後に。ここが決まらないうちに節を作らない
2. **節ごとに、先にデータ（表・図）を置く。**文章は後から、表の前の1文として足す
3. **数字は必ず表か図に載せてから本文で触れる。**R9 が警告を出したら、本文を削るのではなく
   データを足すほうを先に考える
4. **限界は節の中に置く。**末尾にまとめて隔離すると読まれない

## やってはいけないこと

- **HTML を直接編集して publish する。**次に JSON から描いたときに消える。JSON を直す
- **`svg` ブロックにグラフを書く。**データのグラフは 4 種のどれかで描く。`svg` は流れ図だけ
- **表を畳まずに並べる。**8 行を超えたら畳む。畳んだ中身は削らない（検証中は全データを載せる）
- **`source` を `measured` で埋める。**仮想で出した数字を実測と書くのが、この研究で最も悪い誤り

## 送信前

`report` Skill（テキストの報告）と `troubles` Skill を先に回す。
**HTML レポートは、テキストの報告の代わりにはならない。**問いへの答えは文章で書く。
